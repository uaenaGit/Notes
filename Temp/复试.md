## 一、计算机基础课程复试面试题

### 1.1 数据结构

#### 1.1.1 线性结构

**数组与链表**

|特性|数组|链表|
|:--|:--|:--|
|访问|O(1)随机访问|O(n)顺序访问|
|插入删除|O(n)|O(1)(已知位置)|
|内存|连续|离散|
|大小|固定|动态|

**常考问题**

- **数组和链表的应用场景？**
    - 数组：查询多、修改少、已知大小
    - 链表：频繁插入删除、大小未知
- **单链表反转实现？**

```c
ListNode* reverse(ListNode* head) {
    ListNode *prev = NULL, *curr = head;
    while (curr) {
        ListNode* next = curr->next;
        curr->next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}
```

**栈与队列**

**常考问题**

- **栈的应用场景？**
    - 函数调用栈、表达式求值、括号匹配、DFS
- **队列的应用场景？**
    - BFS、任务调度、缓冲区
- **用两个栈实现队列？**

```cpp
class Queue {
    stack<int> s1, s2;
public:
    void push(int x) { s1.push(x); }
    int pop() {
        if (s2.empty())
            while (!s1.empty()) { s2.push(s1.top()); s1.pop(); }
        int val = s2.top(); s2.pop();
        return val;
    }
};
```

#### 1.1.2 树与图

**二叉树**

**常考问题**

- **二叉树遍历方式？**
    - 前序：根→左→右
    - 中序：左→根→右
    - 后序：左→右→根
    - 层序：BFS
- **二叉搜索树(BST)特性？**
    - 左子树 < 根 < 右子树
    - 中序遍历得到有序序列
- **平衡二叉树(AVL)与红黑树区别？**

|特性|AVL|红黑树|
|:--|:--|:--|
|平衡度|严格平衡|近似平衡|
|旋转次数|多|少|
|适用场景|查询多|插入删除多|
|STL实现|-|map/set|

**图**

**常考问题**

- **图的存储方式？**
    - 邻接矩阵：适合稠密图，O(1)查边
    - 邻接表：适合稀疏图，节省空间
- **DFS与BFS区别？**

|特性|DFS|BFS|
|:--|:--|:--|
|数据结构|栈/递归|队列|
|应用|连通性、拓扑排序|最短路径(无权)|
|空间复杂度|O(h)|O(w)|

- **最短路径算法？**
    - Dijkstra：单源，无负权边，O(ElogV)
    - Bellman-Ford：单源，可处理负权，O(VE)
    - Floyd：多源，O(V³)

#### 1.1.3 哈希与排序

**哈希表**

**常考问题**

- **哈希冲突解决方法？**
    - 链地址法（拉链法）
    - 开放地址法（线性探测、二次探测）
    - 再哈希法
- **哈希函数设计原则？**
    - 均匀分布、计算简单、减少冲突

**排序算法**

|算法|时间复杂度(平均)|空间复杂度|稳定性|
|:--|:--|:--|:--|
|冒泡|O(n²)|O(1)|稳定|
|选择|O(n²)|O(1)|不稳定|
|插入|O(n²)|O(1)|稳定|
|快排|O(nlogn)|O(logn)|不稳定|
|归并|O(nlogn)|O(n)|稳定|
|堆排|O(nlogn)|O(1)|不稳定|

**常考问题**

- **快速排序原理？**
    - 选基准、分区、递归
    - 最坏情况：已有序，O(n²)
- **堆排序原理？**
    - 建大顶堆、交换堆顶与末尾、调整堆
- **何时使用哪种排序？**
    - 小数据：插入排序
    - 大数据：快排/归并
    - 要求稳定：归并
    - 空间受限：堆排

### 1.2 计算机组成原理

#### 1.2.1 数据表示

**常考问题**

- **原码、反码、补码？**
    - 正数：三者相同
    - 负数：原码符号位1，反码除符号位取反，补码=反码+1
    - 补码优势：统一加减运算、0唯一表示
- **IEEE 754浮点数格式？**

```
单精度(32位)：1位符号 + 8位阶码(偏置127) + 23位尾数
双精度(64位)：1位符号 + 11位阶码(偏置1023) + 52位尾数
```

- **大端与小端？**
    - 大端：高位字节存低地址（网络字节序）
    - 小端：低位字节存低地址（x86架构）

#### 1.2.2 存储系统

**常考问题**

- **Cache映射方式？**

|方式|优点|缺点|
|:--|:--|:--|
|直接映射|简单快速|冲突率高|
|全相联|灵活|成本高|
|组相联|折中|实现复杂|

- **Cache替换算法？**
    - FIFO、LRU、Clock、随机
- **虚拟存储器层次？**

```
寄存器 → Cache → 主存 → 磁盘
(最快/最小/最贵) (最慢/最大/最便宜)
```

- **TLB作用？**
    - 页表缓存，加速地址翻译
    - 缺页时先查TLB，再查页表

#### 1.2.3 指令系统与CPU

**常考问题**

- **CISC与RISC区别？**

|特性|CISC(x86)|RISC(ARM)|
|:--|:--|:--|
|指令复杂度|复杂|简单|
|指令长度|可变|固定|
|寻址方式|多|少|
|流水线|难优化|易优化|

- **流水线冒险类型？**
    - 结构冒险：资源冲突
    - 数据冒险：数据依赖（前推解决）
    - 控制冒险：分支跳转（分支预测解决）
- **中断处理流程？**

```
保存现场 → 关中断 → 执行中断服务程序 → 开中断 → 恢复现场
```

#### 1.4.2 TCP/IP协议

**常考问题**

- **TCP三次握手？**

```
客户端                    服务器
  │                         │
  │─── SYN (seq=x) ────────>│  1
  │                         │
  │<── SYN+ACK (seq=y,ack=x+1) ─│  2
  │                         │
  │─── ACK (ack=y+1) ──────>│  3
```

- 为什么三次？防止失效连接、确认双方收发能力
- **TCP四次挥手？**

```
主动关闭                被动关闭
  │─── FIN ─────────────>│
  │<─── ACK ─────────────│
  │<─── FIN ─────────────│
  │─── ACK ─────────────>│
```

- 为什么四次？ACK和FIN可分开发送
- **TCP可靠性保证？**
    - 校验和、序列号、确认应答、超时重传、流量控制、拥塞控制
- **TCP流量控制vs拥塞控制？**

|类型|目的|机制|
|:--|:--|:--|
|流量控制|防止接收方溢出|滑动窗口|
|拥塞控制|防止网络过载|慢启动/拥塞避免/快重传/快恢复|

### 2.1 C语言核心考点

#### 2.1.1 基础语法

**关键字理解**

|关键字|作用|常考点|

**常考问题**

- **static的三种用法？**

```c
// 1. 修饰局部变量：延长生命周期
void func() {

}

// 2. 修饰全局变量：限制文件作用域
static int global_var;  // 仅本文件可见

// 3. 修饰函数：限制文件作用域
static void helper() {}  // 仅本文件可调用
```

- **const指针辨析？**

```c
const int *p1;      // 指向常量的指针，内容不可改
int *const p2;      // 常量指针，指针不可改
const int *const p3; // 都不可改
```

- **volatile作用？**

```c
volatile int flag;  // 每次从内存读取，不缓存到寄存器
// 场景：多线程共享变量、硬件寄存器、信号处理
```

#### 2.1.4 常考代码实现

**strcpy实现**

```c
char* strcpy(char* dest, const char* src) {
    assert(dest && src);
    char* ret = dest;
    while ((*dest++ = *src++) != '\0');
    return ret;
}
```

**memcpy实现**

```c
void* memcpy(void* dest, const void* src, size_t n) {
    char* d = (char*)dest;
    const char* s = (const char*)src;
    while (n--) *d++ = *s++;
    return dest;
}
```

**字符串反转**

```c
void reverse(char* str) {
    if (!str) return;
    char *start = str, *end = str + strlen(str) - 1;
    while (start < end) {
        char tmp = *start;
        *start++ = *end;
        *end-- = tmp;
    }
}
```

### 2.2 C++语言核心考点

#### 2.2.1 面向对象基础

**常考问题**

- **封装、继承、多态？**
    - 封装：隐藏实现，提供接口

- **访问控制符？**

|修饰符|本类|子类|外部|
|:--|:--|:--|:--|
|public|✓|✓|✓|
|protected|✓|✓|✗|

- **继承方式？**

```cpp
class A { public: int x; protected: int y; private: int z; };
class B : public A {};    // x公,y保,z不可见
class C : protected A {}; // x保,y保,z不可见
class D : private A {};   // x私,y私,z不可见
```

#### 2.2.2 虚函数与多态

**常考问题**

- **虚函数实现原理？**

```
对象 → vptr(虚表指针) → vtable(虚函数表) → 函数地址
```

- 运行时绑定，支持多态
- **虚函数表布局？**

```cpp
class Base {
    virtual void func1() {}
    virtual void func2() {}
};
// 对象内存：[vptr][成员变量]
// vtable: [func1地址][func2地址]
```

- **纯虚函数与抽象类？**

```cpp
class Shape {
public:
    virtual double area() = 0;  // 纯虚函数
    virtual ~Shape() {}         // 虚析构函数

// 含纯虚函数的类不能实例化
```

- **为什么析构函数要虚？**

```cpp
Base* p = new Derived();
delete p;  // 基类析构非虚，Derived析构不执行，内存泄漏
```

## 四、用户态 so 和内核态 ko 的区别

### 4.1 基本概念对比

|特性|用户态 so (Shared Object)|内核态 ko (Kernel Object)|
|:--|:--|:--|
|**运行空间**|用户空间|内核空间|
|**加载方式**|`dlopen()` 动态加载|`insmod/modprobe` 加载|
|**链接库**|可链接其他 so 库|只能链接内核导出符号|
|**权限级别**|Ring 3|Ring 0|
|**内存访问**|只能访问用户内存|可访问全部内存|
|**稳定性要求**|崩溃只影响进程|崩溃导致内核 panic|
|**调试方式**|gdb|kgdb/printk/ftrace|
|**文件位置**|`/lib`, `/usr/lib`|`/lib/modules/$(uname -r)/`|

### 4.2 为什么要有内核态 ko

**核心原因**

1. **硬件直接访问**
    - 内核模块可以直接访问硬件寄存器
    - 用户态程序需要通过系统调用间接访问
2. **高性能需求**
    - 避免用户态/内核态切换开销
    - 直接操作内存和 DMA
3. **系统服务扩展**
    - 文件系统、网络协议栈、设备驱动等需要内核支持
    - 提供系统调用接口给用户态
4. **全局资源管理**
    - 内存管理、进程调度、中断处理等需要内核权限

**典型应用场景**

```
用户态 so                    内核态 ko
├── 应用程序库               ├── 设备驱动 (网卡/存储)
├── 动态链接库               ├── 文件系统 (ext4/btrfs)
├── 中间件 (Redis/Nginx模块)  ├── 网络协议栈扩展
└── 第三方 SDK               └── 安全模块 (SELinux)
```

### 4.3 加载机制对比

**用户态 so 加载**

```c
// 动态加载

void *func = dlsym(handle, "my_function");
func();
dlclose(handle);
```

```bash

# 卸载模块

```

```c
    printk(KERN_INFO "Module loaded\n");
```

## 五、内核编程注意点和常考面试题

### 5.1 内核编程注意事项

**内存管理**

| 分配函数                  | 使用场景          | 能否睡眠            |
| :-------------------- | :------------ | :-------------- |
| `kmalloc()`           | 小内存 (< 128KB) | 可以 (GFP_KERNEL) |
| `kzalloc()`           | 初始化为 0 的小内存   | 可以              |
| `vmalloc()`           | 大内存 (连续虚拟地址)  | 可以              |
| `kmalloc(GFP_ATOMIC)` | 中断上下文         | **不能睡眠**        |
| `kfree()`             | 释放 kmalloc 内存 | -               |
| `vfree()`             | 释放 vmalloc 内存 | -               |
GFP_KERNEL 的行为

是内核中最常用的分配标志，用于进程上下文。

分配内存时 可能睡眠：如果内存不足，内核会唤醒 kswapd 回收内存，或让当前进程进入睡眠等待内存释放。

因此，只能在进程上下文中使用，不能用于中断上下文或自旋锁保护的临界区。
GFP_ATOMIC 的行为

用于 原子上下文（如中断处理程序、软中断、自旋锁内）。

分配内存时 不会睡眠：如果内存不足，直接返回失败（NULL），不会阻塞等待。

为了保证在不睡眠的情况下尽量成功，内核会预留一部分内存供原子分配使用。


**同步机制**

|机制|使用场景|能否睡眠|
|:--|:--|:--|
|自旋锁 (spinlock)|中断上下文/短临界区|**不能睡眠**|
|互斥锁 (mutex)|进程上下文/长临界区|可以睡眠|
|信号量 (semaphore)|资源计数|可以睡眠|
|读写锁 (rwlock)|读多写少场景|不能睡眠|
|RCU|读多写少/高性能场景|读端无锁|

**中断处理**

```c
// 中断注册
request_irq(irq_num, handler, flags, name, dev_id);

// 中断上下文注意事项
// 1. 不能睡眠
// 2. 不能使用 mutex
// 3. 不能调用 kmalloc(GFP_KERNEL)
// 4. 执行时间要短，耗时操作放 bottom half
```

## 六、ioctl 函数的作用

### 6.1 基本概念

**ioctl 定义**

```c
// 用户态调用
int ioctl(int fd, unsigned long request, ...);

// 内核态实现
long (*unlocked_ioctl)(struct file *file, 
                       unsigned int cmd, 
                       unsigned long arg);
```

**核心作用**：用户态和内核态之间的**控制命令通信接口**

### 6.2 使用场景

|场景|示例|
|:--|:--|
|设备配置|设置网卡参数、波特率|
|状态查询|获取设备状态、寄存器值|
|控制命令|启动/停止设备、复位|
|数据传递|传递小量控制数据|

### 6.3 实现示例

**内核态实现**

```c
#define IOC_MAGIC 'k'
#define IOC_SET_DATA _IOW(IOC_MAGIC, 1, struct my_data)
#define IOC_GET_DATA _IOR(IOC_MAGIC, 2, struct my_data)

static long my_ioctl(struct file *file, 
                     unsigned int cmd, 
                     unsigned long arg)
{
    struct my_data data;
    switch (cmd) {
    case IOC_SET_DATA:
        if (copy_from_user(&data, (void __user *)arg, sizeof(data)))
            return -EFAULT;
        // 处理数据
        break;
    case IOC_GET_DATA:
        // 获取数据
        if (copy_to_user((void __user *)arg, &data, sizeof(data)))
            return -EFAULT;
        break;
    default:
        return -ENOTTY;
    }
    return 0;
}
```

**用户态调用**

```c
int fd = open("/dev/mydevice", O_RDWR);
struct my_data data;

// 设置数据
ioctl(fd, IOC_SET_DATA, &data);

// 获取数据
ioctl(fd, IOC_GET_DATA, &data);

close(fd);
```

### 6.4 常考问题

**问题 1：ioctl 和 read/write 的区别？**

|特性|read/write|ioctl|
|:--|:--|:--|
|用途|数据传输|控制命令|
|数据量|大量数据|小量控制数据|
|语义|流式读写|命令 + 参数|

**问题 2：`copy_from_user` 和 `copy_to_user` 的作用？**

- 安全地在用户态和内核态之间拷贝数据
- 检查指针合法性，防止内核访问非法用户地址
- **必须使用**，不能直接解引用用户指针

**问题 3：ioctl 命令编号如何生成？**


## 八、UB 架构相关

### 8.1 SSU 和 UB 的关系

SSU（Solid State Unit，固态存储单元）是UB（Unified Bus，统一总线）互联架构中的一种**资源池化节点**，而UB是将这些节点连接起来的统一互联协议。

在UB的架构设计中，所有计算资源都被抽象为**对等的节点**，通过UB总线互联成一台"逻辑计算机"。SSU作为存储节点，与其他节点（CPU、GPU、NPU、MEM、DPU等）处于**对等地位**，通过UB协议进行高效通信。

**具体来说：**

- **SSU内部包含多个子模块**：UBIP（UB接口处理器）、UCP芯片、UCP固件、FCP子系统、SSD等组件
- **UBIP负责收包**：处理来自UB总线的网络协议报文，完成底层协议解析
- **UCP负责解包和业务处理**：解析UBIP传递的数据，还原出I/O请求，分发给FCP处理SSD访问

SSU通过UB总线与CPU、GPU等节点互联，实现存储资源的池化和远程直接访问。这种设计使得其他节点可以像访问本地内存一样访问SSU中的存储资源。

### 8.2 为什么要研发 UB

**UB诞生的根本原因**：**总线与网络的割裂**，以及AI大模型时代对超大规模、超低延迟互联的迫切需求。

**传统PCIe的不足：**

- **主从架构瓶颈**：PCIe是典型的"CPU主、设备从"架构，所有I/O操作都需要CPU介入
- **扩展性差**：PCIe总线受限于物理距离和设备数量，无法构建大规模集群
- **延迟较高**：数据路径长，需要经过多层软件栈

**RoCE的不足：**

- **仍然依赖PCIe**：RoCE网卡本身通过PCIe连接到CPU
- **软件栈开销**：虽然RDMA实现了内核旁路，但RoCE仍然需要经过网卡驱动和PCIe总线
- **扩展性与延迟的折中**：以太网本身是松耦合设计，延迟（微秒级）远高于总线（纳秒级）

**NVLink的不足：**

- **私有协议**：NVLink是Nvidia的私有技术，不对外开放
- **扩展性有限**：主要面向GPU-GPU互联，无法构建超大规模统一互联
- **与CPU生态隔离**：主要与IBM POWER处理器合作，x86生态无法原生支持

**UB的核心价值：**

- **对等架构**：所有设备都是平等的，任何设备都可以通过Load/Store内存语义直接访问其他设备的内存
- **统一抽象**：无论是超节点内的高速电信号背板，还是超节点间的长距离光纤，UB都提供统一的内存语义
- **超大规模扩展**：支持8192个节点无缝互联
- **开源生态**：UB 2.0开始采取全面开源策略

### 8.3 SPU 的功能

SPU（Service Processing Unit，服务处理单元）在SSU内部扮演**控制面处理器**的角色，类似CPU但专注于服务管理和异常处理。

**可能承担的功能：**

|功能类别|具体内容|
|:--|:--|
|**会话与资源管理**|会话建立、状态维护、资源仲裁|
|**异常处理中心**|错误收集与上报、重试与恢复、日志与告警|
|**控制面协议处理**|建链与拆链、参数协商、状态机管理|
|**安全与权限控制**|内存保护、访问控制|
|**与UCP微码的分工**|SPU负责控制面，UCP负责数据面|

### 8.4 建链流程

**建链是RDMA QP之间正式通信前必须进行的准备工作**

**4.1 建链前准备**

- 两端SSU节点各自创建QP（Queue Pair），获得本端QPN
- 两端各自注册内存区域（MR），获得R_Key和虚拟地址（VA）
- 两端通过UB总线建立底层物理链路（L1/L2已就绪）

**4.2 建链流程（以RC服务类型为例）**

|阶段|内容|
|:--|:--|
|**第一阶段：控制通道建立**|两端通过Socket API或CM建立TCP/IP连接|
|**第二阶段：交换建链参数**|交换GID、QPN、VA、R_Key、Q_Key等必要信息|
|**第三阶段：QP状态迁移**|INIT → RTR → RTS|
|**第四阶段：同步与确认**|确保接收端已经Post Receive WR后再触发发送|

**4.3 在UB架构中的体现**

- **控制面**：建链的参数交换由SPU处理
- **数据面**：建链完成后，UCP微码可以直接进行RDMA读写操作

## 九、RDMA 核心机制

### 9.1 数据到达感知方式

|方式|说明|适用场景|
|:--|:--|:--|
|**中断**|网卡更新CQ后触发MSI-X中断，CPU响应中断并处理CQE|低负载场景|
|**轮询**|用户态程序主动循环检查CQ中的CQE|低延迟场景（推荐）|

### 9.2 三大核心机制

**1. 零拷贝（Zero Copy）**

- **内存注册**：应用程序通过 `ibv_reg_mr` 向网卡驱动注册内存区域
- **直接DMA**：网卡硬件根据内存句柄查询MTT，直接从用户态缓冲区DMA读取数据
- **关键点**：零拷贝的实现依赖内存注册和DMA硬件

**2. 内核旁路（Kernel Bypass）**

- **用户态驱动**：RDMA提供用户态Verbs API（如 `ibv_post_send`、`ibv_poll_cq`）
- **直接操作硬件**：通过内存映射（mmap）将网卡的门铃寄存器和完成队列映射到用户空间
- **关键点**：控制面与数据面分离，数据面完全在用户态运行

**3. 协议卸载（Protocol Offload）**

- **传输层卸载**：网卡硬件内部实现完整的传输层逻辑（可靠性、流控、重传等）
- **头部处理**：网卡硬件负责生成和解析RDMA协议头部
- **关键点**：CPU完全不再感知单个数据包的收发

**三大机制的协同关系：**

- **零拷贝**是基础：消除数据在内存间的复制
- **内核旁路**是通道：让应用程序直接驱动网卡
- **协议卸载**是升华：将协议处理下沉到硬件

## 十一、UCP 芯片与微码

### 11.1 核心定位

UCP硬件是**物理芯片**，而UCP微码是**运行在该芯片上的固件程序**。两者的关系类似于CPU（硬件）与操作系统内核（软件）的关系。

### 11.2 UCP 硬件的职责（"身体"）

|功能模块|说明|
|:--|:--|
|**队列引擎**|硬件实现SQ、RQ、CQ的管理单元，支持无锁环形队列操作|
|**门铃机制**|提供门铃寄存器，写入可触发硬件处理队列中的WQE|
|**DMA引擎**|内置DMA控制器，直接访问主机内存或其他设备内存|
|**中断控制器**|管理中断源，触发中断通知CPU或微码|
|**协议卸载引擎**|实现传输层的可靠性、流控、数据包排序等逻辑|
|**寄存器堆**|提供控制状态寄存器，用于配置设备、查询状态、复位等|

### 11.3 UCP 微码的职责（"灵魂"）

|功能模块|说明|
|:--|:--|
|**解析WQE**|从发送队列中取出WQE，解析操作码、地址、长度等信息|
|**业务逻辑编排**|决定将任务转发给哪个后端模块，构造后端命令格式|
|**异常处理**|检测错误时上报SPU，执行初步恢复动作|
|**中断处理**|响应硬件中断，执行上半部快速处理|
|**状态维护**|维护QP或连接的状态机，配合SPU完成建链流程|
|**资源管理**|管理硬件队列的指针，确保与硬件的一致性|

## 十二、正常路径 IO 和异常上报

### 12.1 正常 I/O 路径流程

```
1. 接收 I/O 请求 → 2. 合法性检查 → 3. 封装 API → 4. 转发给 FCP → 5. 等待完成
```

**合法性检查内容：**

- 操作类型：是否为支持的读、写或其他管理命令
- 地址与长度：检查起始地址是否对齐，长度是否超限
- 数据缓冲区：检查缓冲区指针是否有效
- 标志位：检查是否有冲突或无效的标志组合

### 12.2 异常处理

**FCP 处理错误时：**

- FCP 将处理结果通过**完成队列返回给 UCP**
- UCP 解析完成状态，向上层返回相应错误码
- 对于可重试的错误，UCP 可能将请求重新入队或触发重试机制

### 12.3 与故障路径的协同

**链路故障（linkdown）时的处理：**

- UCP 收到 linkdown 事件后，设置全局标志表示链路已 down
- 新到达的 I/O 请求直接返回"链路不可用"错误
- 已发送给 FCP 但未完成的 I/O，等待 FCP 返回结果或超时
- 所有 I/O 处理完毕后，执行资源排空和队列删除

### 12.4 并发处理

- 采用**每 CPU 的数据结构**和**无锁队列**避免锁竞争
- 每个 CPU 有自己的 I/O 请求队列
- 使用无锁环形队列，通过原子操作更新生产者和消费者指针
- 全局访问资源使用 `READ_ONCE`/`WRITE_ONCE` 配合内存屏障

## 十三、芯片复位

### 13.1 芯片复位的基本概念

芯片复位是指将整个芯片（或芯片中的某个子系统）恢复到已知的初始状态的操作。当系统遇到无法通过正常异常处理机制恢复的严重故障时，复位是最后一道防线。

### 13.2 复位的主要类型

|复位类型|CPU|外设|RAM|寄存器|恢复速度|
|:--|:--|:--|:--|:--|:--|
|上电复位|全复位|全复位|清零|全复位|慢|
|系统复位|全复位|全复位|保持|全复位|中|
|应用复位|部分复位|部分复位|保持|部分复位|快|

### 13.3 复位后的操作流程

```
1. 硬件复位信号产生 → 2. Boot ROM 执行 → 3. 应用程序启动
```

**Boot ROM 执行内容：**

- 检测调试器连接
- 读取复位原因寄存器
- 根据引导模式选择启动源

**应用程序启动内容：**

- C 运行环境初始化
- 外设重新初始化
- 恢复业务上下文（如需要）

### 13.4 复位与中断设计的关系

**中断处理中可能触发复位的场景：**

- 中断风暴：某个中断源持续触发且无法被正常处理
- 中断处理超时：上半部执行时间过长或下半部被长时间阻塞
- 不可恢复的硬件错误：DMA 访问越界、关键寄存器读取失败

**复位对中断系统的影响：**

- 复位会**禁用所有中断**
- 复位后，中断控制器需要**重新初始化**
- 复位原因寄存器会**记录最后一次复位源**

### 13.5 分级复位策略

|级别|复位范围|适用场景|
|:--|:--|:--|
|**第一级**|子系统软复位|仅复位出问题的模块（如 DMA 引擎）|
|**第二级**|应用复位|复位整个 UCP 微码，保留 RAM 中的关键状态|
|**第三级**|系统复位|复位整个芯片，完全重新初始化|

## 十四、LINKDOWN 处理

### 14.1 业务层通知 UCP 微码的机制

**整体架构与数据流：**

```
MAC 层驱动（内核模块）→ 业务层进程（用户态）→ UCP 微码（libucp.so）
```

**注册阶段：UCP 微码向业务层注册回调**

```c
// 业务层头文件（业务层对外提供的注册接口）
typedef void (*ucp_event_cb)(int device_id, int event_type, void *user_data);
int business_register_callback(int event_type, ucp_event_cb cb, void *user_data);

// libucp.so 内部
static void ucp_linkdown_handler(int dev_id, int event, void *data) {
    // 处理 linkdown 的具体逻辑
}

__attribute__((constructor))
static void ucp_register_handlers(void) {
    business_register_callback(EVENT_LINKDOWN, ucp_linkdown_handler, NULL);
    business_register_callback(EVENT_LINKUP, ucp_linkup_handler, NULL);
}
```

**业务层事件循环（基于 epoll）**

```c
int epfd = epoll_create1(0);
struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = netlink_fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, netlink_fd, &ev);

while (1) {
    struct epoll_event events[64];
    int nfds = epoll_wait(epfd, events, 64, -1);  // 阻塞等待事件
    for (int i = 0; i < nfds; i++) {
        if (events[i].data.fd == netlink_fd) {
            // 读取 netlink 消息
            // 调用注册的回调
            callback_table[event_type].cb(device_id, event_type, user_data);
        }
    }
}
```

### 14.2 MAC 层在 linkdown 时的动作

**MAC 层完成动作：**

- **记录链路状态**：将内部状态寄存器标记为 `LINK_DOWN`
- **屏蔽或延迟上报**：实现链路去抖动（link debouncing）机制
- **硬件自恢复尝试**：某些硬件支持自动重试

**重复 linkdown 信号的处理：**

|机制|说明|
|:--|:--|
|**去抖动（Debouncing）**|MAC 驱动维护链路状态机，只有状态发生变化时才上报|
|**上层去重**|UCP 业务层通过状态机去重，忽略重复事件|
|**硬件辅助去抖**|网卡硬件内部已实现去抖逻辑|

### 14.3 链路恢复过程

**完整的链路恢复时序：**

```
1. 物理介质恢复 → 2. MAC 硬件检测 → 3. MAC 驱动上报 → 
2. 业务层收到事件 → 5. UCP 重建资源 → 6. 上层协议建链
```

**关键点：**

- **步骤 1-2 完全由硬件自动完成**
- **步骤 3 是驱动对硬件事件的响应**
- **步骤 4-6 是软件层面的恢复**

### 14.4 上层协议建链

**建链通常需要完成的任务：**

|任务|说明|
|:--|:--|
|**状态机迁移**|QP 从 INIT/RTR/ERROR 状态迁移到 RTS 状态|
|**参数协商与交换**|交换 QPN、序列号、MTU、重传超时参数、R_key 等|
|**资源绑定与映射**|将上层连接与底层硬件资源进行绑定|
|**交换对端信息**|通过 CM 协议交换设备信息|
|**激活数据面通路**|硬件认为该连接已经"可用"|

**建链失败处理：**

- **重试策略**：指数退避、最大重试次数
- **重试触发者**：上层协议栈（plog）负责，UCP 微码不参与
- **重试失败后**：向上层应用报告失败、释放资源、触发管理平面介入

## 十五、中断处理

### 15.1 中断基础概念

**什么是中断？**  
中断是硬件或软件向 CPU 发出的异步事件，用于通知 CPU 需要处理某个紧急任务。

**中断处理阶段：**

```
中断请求（硬件触发）→ 中断响应（保存现场并跳转）→ 中断处理（执行 ISR）
```

**上半部和下半部的区别：**

|特性|上半部|下半部|
|:--|:--|:--|
|执行上下文|中断上下文|进程上下文/软中断上下文|
|能否睡眠|不能|可以（workqueue）|
|执行时间|极短|可较长|
|典型任务|快速响应硬件、屏蔽中断、记录状态|耗时操作|

**Linux 下半部机制对比：**

|机制|执行上下文|能否睡眠|并发性|典型用途|
|:--|:--|:--|:--|:--|
|软中断|原子|否|同类型可多 CPU 并发|高性能网络、块设备|
|tasklet|原子|否|同一 tasklet 串行|简单设备驱动|
|workqueue|进程|是|线程池管理|需要睡眠或长时间处理|

### 15.2 多级中断处理

**为什么要先 mask 一级中断再 clear 一级中断？**

|操作|作用|
|:--|:--|
|**mask（屏蔽）**|关闭中断使能位，防止中断嵌套，保护临界区|
|**clear（清除）**|清除挂起状态位，告诉硬件该中断已被接受|

**顺序的重要性：**

- **先 mask 后 clear**：确保在清除挂起位之前，该中断已经被屏蔽
- **如果先 clear 后 mask**：在 clear 执行后、mask 执行前的间隙内，新中断可能产生并被误清除，导致中断丢失

**中断源汇聚处理流程：**

```
1. mask 一级中断 → 2. clear 一级中断 → 3. 遍历二级中断源 → 
2. 如有三级继续遍历 → 5. 记录所有触发源 → 6. 调度下半部
```

### 15.3 volatile 关键字

**核心作用：**  
`volatile` 禁止编译器对变量的访问进行优化，确保每次访问都直接操作内存。

**典型使用场景：**

- 硬件寄存器映射
- 中断服务程序共享的变量
- 多线程环境中的简单标志

**volatile 不能做什么：**

- 不保证原子性
- 不保证内存可见性（多核系统）
- 不解决数据竞争

**Linux 内核中的替代方案：**

- `READ_ONCE()` / `WRITE_ONCE()`
- 原子操作（`atomic_t`）
- 显式内存屏障（`smp_mb()`）

### 15.4 work_queue 机制

**workqueue 机制的特点：**

- **进程上下文执行**：可以睡眠、使用互斥锁、进行可能导致阻塞的内存分配
- **可被调度与抢占**：由 Linux 调度器调度
- **并发管理**：CMWQ 框架自动管理工作线程的并发
- **使用简单**：`DECLARE_WORK` / `INIT_WORK` 初始化，`schedule_work()` 调度

**为什么选用 workqueue：**

- 允许睡眠（满足下半部中可能出现的睡眠需求）
- 实现简单可靠
- 符合驱动规范
- 资源开销适中

**初始化 work_struct：**

```c
// 动态初始化，嵌入设备结构体中
struct ssu_device {
    struct work_struct work;
    // ... 其他成员
};

INIT_WORK(&dev->work, work_handler);
schedule_work(&dev->work);
```

### 15.5 设备 probe

**probe 的定义：**  
设备 probe 是 Linux 内核驱动模型中的核心概念，是驱动和设备进行"配对"并建立联系的函数。

**probe 的调用时机：**

- 系统启动时，内核枚举所有总线上的设备
- 热插拔时，设备被插入
- 驱动加载时，如果设备已经存在而驱动之后才加载

**典型的 probe 函数完成工作：**

- 检查设备是否存在
- 分配设备结构体
- 映射硬件资源
- 初始化内核机制（锁、工作队列等）
- 注册中断处理函数
- 初始化硬件

### 15.6 中断汇聚

**中断源汇聚的概念：**  
在多级中断控制器架构中，多个下层中断源共享一个上层中断线的现象。

**软件层面的处理流程：**

```
1. 进入 ISR 后，立即 mask 一级中断
2. 清除一级中断的挂起状态
3. 遍历所有可能的下级中断源
4. 如有更下一级中断，继续向下遍历
5. 记录所有被触发的来源
6. 根据记录的触发源，分别调用对应的中断处理程序
```

**中断源汇聚与共享中断的区别：**

- **中断源汇聚**：发生在硬件层次，多个下层设备通过同一根中断线上报
- **共享中断**：发生在软件层次，多个设备注册时使用同一个中断号
