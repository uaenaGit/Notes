**轮询（polling）**：内核定期对设备的状态进行查询，然后做出相应的处理。

# 7.1 中断
1. 中断随时可以产生。
2. x86体系架构中，通过陷入内核引起一种特殊的异常——系统调用处理程序异常。

# 7.2 中断处理程序

1. 内核响应一个特定中断的时候，内核会执行一个函数，叫做中断处理函数或者中断服务例程（ISR）。
2. Linux中，中断处理程序就是普通 C函数，只是这些函数必须按照特定的类型声明，以便内核能够以标准的方式传递处理程序的信息。中断处理程序是被内核用来调用响应中断的，运行于中断上下文的特殊上下文中。中断上下文也称原子上下文，该上下文中执行的代码不可阻塞。

# 7.3 上半部和下半部的对比

1. 要想中断处理程序运行得快，又想中断处理程序完成的工作量多，将中断分为上半部（Top half） 和下半部（bottom half）。
	- 上半部：做有严格时序的工作：网卡拷贝网络数据报到内存
	- 下半部：能够允许稍后完成的工作：处理和操作数据包。

# 7.4 注册中断处理程序

驱动程序可以通过 `request_irq()`函数注册一个中断处理程序（`<linux/interrupt.h>`中）。
```cpp
int request_irq(unsigned int irq, // irq表示要分配的中断号
				irq_handler_t handler, // 函数指针，指向处理这个中断的实际中断处理程序
				unsigned long flags,
				const char *name,
				void *dev)
typedef irqreturn_t (*irq_handler_t) (int, void*);
```
## 7.4.1 中断处理程序标志

第三个参数`flags`可以为0，也可以是下列一个或多个标志的位掩码。
- IRQF_DISABLED
- IRQ_TIMER
- IRQF_SHARED：可以在多个中断处理程序之间共享中断线。
> 中断处理程序都是预先在内核进行注册的回调函数，不同的函数位于不同的驱动程序中。

`request_irq`成功执行返回0，非0表示有错误发生。该函数可能睡眠，不能在中断上下文或其他不允许阻塞的代码中调用该函数。

## 7.4.3 释放中断处理程序

卸载：注销相应的中断处理程序，并释放中断线。
```c
void free_irq(unsigned int irq, void *dev)
```
### 中断注册与注销函数（Linux 内核）
#### 核心函数速览
| 函数名             | 功能描述                                |
| --------------- | ----------------------------------- |
| `request_irq()` | 在指定的中断线上注册一个中断处理程序（ISR），完成中断线的分配与绑定 |
| `free_irq()`    | 注销指定中断线上的中断处理程序，并释放对应的中断线资源（禁用该中断线） |

#### 函数细节与使用场景
##### `request_irq()`
- **核心作用**：向内核申请并注册一个中断处理函数，将硬件中断号与驱动的中断服务例程关联起来。
- **典型参数**（Linux 内核接口）：
  ```c
  int request_irq(unsigned int irq, irq_handler_t handler, unsigned long flags,
                  const char *name, void *dev);
  ```
  - `irq`：要申请的硬件中断号
  - `handler`：中断发生时被调用的处理函数
  - `flags`：中断属性标志（如 `IRQF_SHARED` 共享中断、`IRQF_TRIGGER_RISING` 上升沿触发等）
  - `name`：中断名称（用于 `/proc/interrupts` 显示）
  - `dev`：共享中断时用于区分不同设备的私有数据指针
- **返回值**：0 表示成功，非 0 表示失败（如中断线已被占用且不支持共享）

##### `free_irq()`
- **核心作用**：释放之前通过 `request_irq()` 申请的中断线，注销对应的中断处理程序，并禁用该中断线。
- **典型参数**：
  ```c
  void free_irq(unsigned int irq, void *dev);
  ```
  - `irq`：要释放的中断号
  - `dev`：与 `request_irq()` 中传入的 `dev` 指针一致，用于匹配要释放的处理程序
- **注意事项**：必须在设备卸载或驱动退出时调用，避免中断资源泄漏；若中断线为共享模式，只有当所有共享该中断的设备都调用 `free_irq()` 后，才会真正禁用中断线。

#### 关联知识点
##### 中断处理流程
1. 硬件触发中断 →  CPU 暂停当前任务 →  保存上下文
2. 内核根据中断号查找已注册的 `request_irq()` 处理函数
3. 执行中断服务例程（`handler`）→  处理硬件事件（如读取数据、清除中断标志）
4. 恢复上下文 →  继续执行被中断的任务

##### 关键概念
- **中断线（IRQ line）**：硬件向 CPU 发送中断信号的物理/逻辑通道，每个中断线对应一个唯一的中断号。
- **共享中断（IRQF_SHARED）**：多个设备可以共享同一条中断线，内核会依次调用所有注册在该线上的处理函数，通过 `dev` 指针区分不同设备。
- **中断上下文**：中断处理函数运行在中断上下文，不能执行阻塞操作（如 `msleep()`、`mutex_lock()`），需保持执行时间极短。

#### 代码示例（驱动模板）
```c
// 中断处理函数
static irqreturn_t my_interrupt_handler(int irq, void *dev_id) {
    // 处理硬件中断（如读取寄存器、清除中断标志）
    return IRQ_HANDLED;
}

// 驱动初始化时注册中断
static int __init my_driver_init(void) {
    int ret;
    ret = request_irq(IRQ_NUM, my_interrupt_handler, IRQF_SHARED,
                      "my_device", &my_dev_data);
    if (ret) {
        pr_err("Failed to request IRQ %d\n", IRQ_NUM);
        return ret;
    }
    return 0;
}

// 驱动退出时注销中断
static void __exit my_driver_exit(void) {
    free_irq(IRQ_NUM, &my_dev_data);
}

module_init(my_driver_init);
module_exit(my_driver_exit);
```

#### 面试/复试考点提示
- **Q**：`request_irq()` 失败的常见原因有哪些？
  - A：中断号无效、中断线已被占用且不支持共享、`flags` 参数非法、内存不足等。
- **Q**：为什么 `free_irq()` 需要传入 `dev` 参数？
  - A：在共享中断场景下，同一个中断线可能绑定多个处理函数，`dev` 指针用于精确匹配要释放的处理程序，避免误删其他设备的中断处理逻辑。
- **Q**：中断处理函数为什么不能执行阻塞操作？
  - A：中断上下文优先级极高，阻塞操作会导致**内核调度异常**，甚至系统死锁；耗时操作应通过 `tasklet` 或 `workqueue` 延后到进程上下文处理。

### 总结
1. `request_irq()` 用于注册中断处理程序，核心参数包含中断号、处理函数、标志位、名称和设备指针，返回值需校验以确保注册成功；`free_irq()` 需与 `request_irq()` 传入的 `dev` 指针一致，避免共享中断场景下的资源释放错误。
2. 中断处理函数运行在中断上下文，禁止阻塞操作，共享中断需通过硬件寄存器判断中断归属并返回对应 `irqreturn_t` 值。
3. 中断线屏蔽机制保证了中断处理程序无重入风险，仅屏蔽当前处理的中断线，不影响系统对其他中断的响应。
# 7.5 编写中断处理程序
### 中断处理程序返回值（irqreturn_t）
#### 核心返回值定义
| 返回值宏       | 含义说明                                                                 |
| -------------- | ------------------------------------------------------------------------ |
| `IRQ_NONE`     | 检测到中断，但该中断并非由当前注册处理函数的设备产生 → 未处理此中断       |
| `IRQ_HANDLED`  | 中断由当前注册处理函数的设备产生，且已被正确处理 → 成功处理此中断         |
| `IRQ_RETVAL(val)` | 辅助宏：`val≠0` 返回 `IRQ_HANDLED`；`val=0` 返回 `IRQ_NONE`，简化返回逻辑 |

#### 核心概念解析
##### 返回值类型 `irqreturn_t`
- 本质是 **`int` 类型**，内核为了兼容性和可读性定义的别名
- 作用：让内核判断中断是否由当前设备真实产生，避免虚假中断干扰

##### 返回值逻辑
- **`IRQ_NONE`**：
  - 场景：共享中断线中，其他设备触发了中断，当前设备只是“被唤醒”但无实际事件
  - 行为：告知内核“这个中断不是我的，我没处理”
- **`IRQ_HANDLED`**：
  - 场景：中断确实是当前设备产生，且已完成硬件寄存器读写、清中断标志等操作
  - 行为：告知内核“这个中断是我的，已经处理完毕”
- **`IRQ_RETVAL(val)`**：
  - 便捷封装：根据处理结果 `val` 自动选择返回值，减少分支代码

##### 内核侧的作用
- 若某条中断线上 **所有处理函数都返回 `IRQ_NONE`**：
  - 内核判定为**虚假中断（未请求的中断）**
  - 可能触发警告或禁用该中断线，避免资源浪费与系统不稳定

#### 代码示例
```c
static irqreturn_t my_irq_handler(int irq, void *dev_id) {
    struct my_dev *dev = dev_id;
    u32 status = readl(dev->base + REG_STATUS);

    // 判断是否是本设备产生的中断
    if (!(status & INT_MASK)) {
        return IRQ_NONE;  // 不是本设备中断 → 返回 IRQ_NONE
    }

    // 处理中断逻辑（清标志、读数据等）
    writel(status | INT_MASK, dev->base + REG_STATUS);

    return IRQ_HANDLED;  // 本设备中断已处理 → 返回 IRQ_HANDLED

    // 或使用 IRQ_RETVAL 简化写法
    // return IRQ_RETVAL(status & INT_MASK);
}
```

#### 复试/面试考点提示
- **Q**：为什么需要区分 `IRQ_NONE` 和 `IRQ_HANDLED`？
  - A：在**共享中断（IRQF_SHARED）** 场景下，一条中断线会绑定多个设备的处理函数。内核需要通过返回值判断：
    1.  该中断是否被至少一个设备真实处理
    2.  若全返回 `IRQ_NONE`，则判定为虚假中断，避免内核无限循环处理无效中断
- **Q**：`irqreturn_t` 为什么要设计成 `int` 的别名？
  - A：为了保持与早期内核版本的兼容性，同时提升代码可读性，让开发者一眼就能看出这是中断处理函数的返回值。
- **Q**：如果中断处理函数忘记清中断标志，会发生什么？
  - A：硬件会持续触发中断，导致内核反复调用处理函数，系统卡顿甚至死锁；此时即使返回 `IRQ_HANDLED`，也会造成严重性能问题。

#### 扩展关联
- 与 `request_irq()`/`free_irq()` 的关系：返回值是共享中断机制的核心组成部分，只有**共享中断**才需要严格区分 `IRQ_NONE`/`IRQ_HANDLED`
- 相关源码：`include/linux/interrupt.h` 中定义 `irqreturn_t` 及相关宏

### 重入和中断处理程序
#### 核心结论
Linux 中的中断处理程序是**无须重入**的，这极大简化了驱动开发。

#### 核心机制
##### 中断屏蔽保护
- 当某个中断处理程序正在执行时，**对应的中断线会在所有处理器上被屏蔽**。
- 这意味着：同一中断线上不会再触发新的中断，避免了同一个中断处理函数被嵌套调用。
- 其他中断线的中断仍然可以正常响应和处理，保证系统整体响应性。

##### 执行特性
- 同一个中断处理程序**绝对不会被同时调用**来处理嵌套的中断。
- 中断处理函数天然具备“原子性”（针对自身中断线），不需要额外处理重入带来的竞态条件。

#### 关键细节
- **屏蔽范围**：仅屏蔽当前正在处理的中断线，其他中断线保持打开。
- **设计目的**：避免中断处理函数的重入，消除了编写中断处理程序时需要考虑的嵌套竞态问题，简化了驱动代码。
- **与共享中断的关系**：即使是共享中断线，在处理函数执行期间，整条中断线都会被屏蔽，因此同一共享线上的所有处理函数都不会被重入调用。

#### 复试/面试考点提示
- **Q**：为什么 Linux 中断处理程序不需要考虑重入？
  - A：因为内核在执行中断处理程序时，会**屏蔽掉对应的中断线**，保证同一中断线上不会产生新的中断，因此同一个处理函数不会被嵌套调用，天然避免了重入问题。
- **Q**：中断屏蔽会影响系统响应吗？
  - A：不会。屏蔽的只是**当前正在处理的中断线**，其他中断线的中断仍然可以被响应和处理，保证了系统对其他硬件事件的实时性。
- **Q**：这和用户态的重入函数有什么区别？
  - A：用户态重入函数需要通过**锁或无锁编程**来保证并发安全；而中断处理程序是通过**硬件中断屏蔽**机制实现“无重入”，不需要软件层面的同步原语。

#### 扩展关联
- 与 `request_irq()` 的关系：注册中断时，内核会自动管理该中断线的屏蔽逻辑，驱动开发者无需手动操作。
- 与中断上下文的关系：中断上下文的原子性也依赖于此机制，保证中断处理期间不会被同类型中断打断。

### 共享的中断处理程序
#### 共享中断 vs 非共享中断处理程序
##### 核心差异（三点关键区别）
| 对比项 | 共享中断处理程序 | 非共享中断处理程序 |
|--------|------------------|--------------------|
| `request_irq()` flags | **必须设置 `IRQF_SHARED`** | 不设置该标志 |
| `dev` 参数 | 必须唯一（不能为 `NULL`），通常传入设备结构体指针 | 可以为 `NULL`（无唯一性要求） |
| 中断处理逻辑 | 必须能判断是否为本设备产生的中断（依赖硬件寄存器+软件判断） | 无需判断，默认中断一定来自本设备 |

##### 详细说明
###### 注册时的 `IRQF_SHARED` 标志
- 共享中断必须在调用 `request_irq()` 时显式指定 `IRQF_SHARED` 标志。
- 注册成功的前提：
  1.  该中断线当前**未被任何程序注册**，或
  2.  该中断线上**所有已注册的处理程序都设置了 `IRQF_SHARED`**。
- 只要有一个注册程序未使用 `IRQF_SHARED`，则该中断线无法被共享。
- 内核版本差异：2.6 及以后版本允许共享处理程序混用 `IRQF_DISABLED`，更早版本则不允许。

###### 唯一的 `dev` 参数
- 共享中断时，`dev` 指针必须**唯一且非空**，用于区分同一条中断线上的不同设备。
- 通常传入设备私有数据结构体指针（如 `struct my_device *`），因为它天然唯一，且中断处理函数可能需要访问设备信息。
- 禁止传入 `NULL`，否则内核无法区分不同设备的处理程序，会导致共享中断逻辑混乱。

###### 中断处理程序必须能区分设备
- 共享中断触发时，内核会**依次调用**该线上所有注册的处理函数。
- 每个处理函数必须通过硬件状态寄存器（如读取中断状态位）判断：
  - 若为本设备产生的中断 → 处理后返回 `IRQ_HANDLED`
  - 若为其他设备产生的中断 → 直接返回 `IRQ_NONE`
- 若硬件不支持“查询中断源”的功能，则无法使用共享中断，因为处理程序无法判断中断归属。

##### 代码示例（共享中断注册）
```c
// 设备私有数据（唯一标识）
struct my_device {
    void __iomem *base;
    // 其他设备信息...
};

static irqreturn_t my_shared_irq_handler(int irq, void *dev_id) {
    struct my_device *dev = dev_id;
    u32 status = readl(dev->base + REG_INT_STATUS);

    // 判断是否为本设备产生的中断
    if (!(status & MY_DEV_INT_MASK)) {
        return IRQ_NONE; // 不是本设备中断
    }

    // 处理本设备中断...
    writel(status | MY_DEV_INT_MASK, dev->base + REG_INT_STATUS);
    return IRQ_HANDLED; // 本设备中断已处理
}

// 注册共享中断
int __init my_shared_irq_init(struct my_device *dev) {
    return request_irq(
        dev->irq,
        my_shared_irq_handler,
        IRQF_SHARED | IRQF_TRIGGER_HIGH, // 必须指定 IRQF_SHARED
        "my_shared_device",
        dev // 传入唯一的设备指针，不可为 NULL
    );
}

// 注销共享中断
void __exit my_shared_irq_exit(struct my_device *dev) {
    free_irq(dev->irq, dev); // 必须传入与注册时相同的 dev 指针
}
```

##### 复试/面试考点提示
- **Q**：为什么共享中断要求 `dev` 参数必须唯一？
  - A：同一条中断线可能绑定多个设备的处理函数，`dev` 指针是内核区分不同处理函数的唯一标识，在调用 `free_irq()` 时也需要用它来精确匹配并注销对应的处理程序。
- **Q**：如果共享中断处理程序不判断中断来源，直接返回 `IRQ_HANDLED` 会有什么后果？
  - A：内核会认为该中断已被处理，不再调用其他设备的处理函数，导致其他设备的中断事件被丢失，系统功能异常。
- **Q**：为什么注册共享中断时，必须所有已注册程序都设置 `IRQF_SHARED`？
  - A：非共享中断会独占中断线，若混合存在，会导致共享中断的设备无法正常触发处理函数，破坏共享机制。

##### 扩展关联
- 与 `irqreturn_t` 的关系：共享中断是 `IRQ_NONE`/`IRQ_HANDLED` 返回值存在的核心场景。
- 与中断重入的关系：共享中断线在处理期间仍会被屏蔽，因此同一处理函数不会被重入调用。

### 总结
1. `irqreturn_t` 核心作用是区分中断归属，共享中断场景下必须严格区分 `IRQ_NONE` 和 `IRQ_HANDLED`，避免虚假中断或中断丢失。
2. Linux 中断处理程序天然无重入风险，核心依赖“中断线屏蔽”机制，仅屏蔽当前处理的中断线，不影响系统整体响应性。
3. 共享中断注册需设置 `IRQF_SHARED` 标志、传入唯一 `dev` 参数，处理程序必须通过硬件寄存器判断中断来源。

## 7.5.2 中断处理程序实例

### RTC 中断处理函数代码解析
#### 函数定义与返回值
```c
static irqreturn_t rtc_interrupt(int irq, void *dev)
```
- **函数类型**：`static irqreturn_t` 表示这是一个静态的中断处理函数，返回值类型为 `irqreturn_t`（中断处理返回类型）。
- **参数**：
  - `irq`：触发的硬件中断号。
  - `dev`：设备私有数据指针（与 `request_irq()` 注册时传入的 `dev` 一致）。
- **返回值**：最终返回 `IRQ_HANDLED`，表示该中断已被本设备正确处理。

---

#### 代码逐行解释
```c
/*
 * 可以是报警器中断、更新完成的中断或周期性中断
 * 我们把状态保存在 rtc_irq_data 的低字节中，
 * 而把从最后一次读取之后所接收的中断号保存在其余字节中
 */
spin_lock (&rtc_lock);
```
- **注释说明**：RTC 中断可能有多种类型（报警、更新、周期性），需要记录中断状态和计数。
- **`spin_lock(&rtc_lock)`**：获取自旋锁 `rtc_lock`，保护对共享变量 `rtc_irq_data` 的并发访问，避免多 CPU 竞争导致数据不一致。

```c
rtc_irq_data += 0x100;
rtc_irq_data &= ~0xff;
rtc_irq_data |= (CMOS_READ(RTC_INTR_FLAGS) & 0xF0);
```
- `rtc_irq_data += 0x100`：高字节部分加 1，用于统计**自上次读取后发生的中断次数**。
- `rtc_irq_data &= ~0xff`：清空低字节，准备写入新的中断状态。
- `rtc_irq_data |= (CMOS_READ(RTC_INTR_FLAGS) & 0xF0)`：
  - 调用 `CMOS_READ(RTC_INTR_FLAGS)` 读取 RTC 硬件的中断标志寄存器。
  - 与 `0xF0` 按位与，提取高 4 位的中断类型信息。
  - 将中断类型写入 `rtc_irq_data` 的低字节，完成状态更新。

```c
if (rtc_status & RTC_TIMER_ON)
    mod_timer(&rtc_irq_timer, jiffies + HZ/rtc_freq + 2*HZ/100);
```
- **条件判断**：检查 RTC 定时器是否已启用（`RTC_TIMER_ON` 标志位）。
- **`mod_timer(...)`**：修改内核定时器 `rtc_irq_timer` 的到期时间：
  - `jiffies`：当前系统时钟节拍数。
  - `HZ/rtc_freq`：根据 RTC 频率计算的定时器间隔（如 `HZ=100` 时，`rtc_freq=100` 则间隔为 1 个节拍）。
  - `+ 2*HZ/100`：添加 20ms 偏移，避免定时器竞争或延迟导致的触发误差。

```c
spin_unlock (&rtc_lock);
```
- 释放自旋锁 `rtc_lock`，结束对 `rtc_irq_data` 的保护。

---

```c
/*
 * 现在执行其余的操作
 */
spin_lock(&rtc_task_lock);
if (rtc_callback)
    rtc_callback->func(rtc_callback->private_data);
spin_unlock(&rtc_task_lock);
```
- **`spin_lock(&rtc_task_lock)`**：获取另一把自旋锁 `rtc_task_lock`，保护回调函数链表的访问。
- **回调执行**：如果 `rtc_callback` 存在（即注册了回调函数），则调用 `rtc_callback->func`，并传入私有数据 `rtc_callback->private_data`，用于执行用户定义的后续处理。
- **`spin_unlock(&rtc_task_lock)`**：释放自旋锁 `rtc_task_lock`。

```c
wake_up_interruptible(&rtc_wait);
```
- 唤醒等待在 `rtc_wait` 等待队列上的进程（通常是用户态读取 RTC 数据的进程），通知其有新的中断事件。

```c
kill_fasync (&rtc_async_queue, SIGIO, POLL_IN);
```
- 向 `rtc_async_queue` 中的异步 I/O 进程发送 `SIGIO` 信号，标记 `POLL_IN` 事件，通知其 RTC 设备有数据可读。

```c
return IRQ_HANDLED;
```
- 告知内核该中断已被本 RTC 设备正确处理，内核无需再调用其他共享中断处理函数。

---

#### 核心设计思想与考点提示
##### 1. 锁的使用
- 使用两把自旋锁 `rtc_lock` 和 `rtc_task_lock` 分别保护不同的共享资源：
  - `rtc_lock`：保护中断状态计数变量 `rtc_irq_data`。
  - `rtc_task_lock`：保护回调函数链表。
- 自旋锁适合**中断上下文**的短时间锁定，避免阻塞操作。

##### 2. 中断上下文限制
- 整个函数运行在**中断上下文**，因此：
  - 不能使用阻塞操作（如 `msleep()`、`mutex_lock()`）。
  - 必须快速执行，避免长时间占用 CPU。
  - 使用 `wake_up_interruptible()` 和 `kill_fasync()` 将耗时操作延后到进程上下文处理。

##### 3. 共享中断兼容性
- 函数最终返回 `IRQ_HANDLED`，表示该中断一定由本 RTC 设备产生。
- 若该中断线为共享模式，内核会根据返回值判断是否需要继续调用其他处理函数。

##### 4. 定时器与异步通知
- 通过 `mod_timer()` 实现周期性 RTC 中断的定时重调度。
- 通过 `wake_up_interruptible()` 和 `kill_fasync()` 实现对用户态的同步/异步通知，支持阻塞读取和异步 I/O 模型。

---

#### 复试/面试考点速问
- **Q**：为什么中断处理函数中要使用自旋锁而不是互斥锁？
  - A：互斥锁会导致阻塞，而中断上下文不能阻塞；自旋锁不会休眠，适合在中断上下文保护短临界区。
- **Q**：`wake_up_interruptible()` 和 `kill_fasync()` 的作用是什么？
  - A：前者唤醒阻塞等待的进程，后者发送异步信号通知用户态，两者都将耗时的业务逻辑延后到进程上下文，保证中断处理的高效性。
- **Q**：`rtc_irq_data` 的设计有什么特点？
  - A：采用“高字节计数+低字节状态”的位分段设计，在一个变量中同时记录中断次数和中断类型，高效利用内存。

---

### 自旋锁（spinlock）vs 互斥锁（mutex）
#### 核心定义与设计理念
| 特性         | 自旋锁（spinlock）| 互斥锁（mutex）|
| ------------ | --------------------------------------------- | --------------------------------------------- |
| 核心逻辑     | 锁被占用时，CPU 循环“自旋”等待，不放弃 CPU 使用权 | 锁被占用时，进程进入睡眠（阻塞），释放 CPU 使用权 |
| 适用场景     | 中断上下文、短临界区（< 100 指令）、多 CPU 场景 | 进程上下文、长临界区（> 100 指令）、单/多 CPU 场景 |
| 睡眠特性     | 不会睡眠，始终占用 CPU                        | 会睡眠，主动让出 CPU 给其他进程                |
| 开销         | 低（无上下文切换），但自旋时消耗 CPU 资源      | 高（有上下文切换），但等待时不消耗 CPU 资源    |
| 死锁风险     | 持有锁时若发生调度/中断，易导致死锁           | 持有锁时可被调度，死锁风险更低（但仍需注意）   |

#### 关键使用规则
##### 自旋锁（spinlock）
1. **使用限制**：
   - 仅能用于**中断上下文**或**进程上下文**的短临界区。
   - 持有自旋锁期间，**禁止执行任何阻塞操作**（如 `msleep()`、`kmalloc(GFP_KERNEL)`、`copy_to_user()`）。
   - 持有自旋锁时，内核会自动屏蔽本地 CPU 的中断（避免中断嵌套导致死锁）。
2. **核心 API**：
   ```c
   // 定义自旋锁
   spinlock_t lock;
   // 初始化自旋锁
   spin_lock_init(&lock);
   // 获取自旋锁（屏蔽本地中断）
   spin_lock_irq(&lock); 
   // 释放自旋锁（恢复本地中断）
   spin_unlock_irq(&lock);
   ```
3. **典型场景**：
   - 中断处理函数中保护共享变量（如 RTC 中断中的 `rtc_lock`）。
   - 内核态短时间的资源竞争（如设备寄存器读写）。

##### 互斥锁（mutex）
1. **使用限制**：
   - 仅能用于**进程上下文**，**禁止在中断上下文使用**（无法睡眠）。
   - 持有互斥锁期间，允许执行阻塞操作（如 I/O、内存分配）。
   - 同一进程只能加锁一次（递归加锁会导致死锁）。
2. **核心 API**：
   ```c
   // 定义并初始化互斥锁
   struct mutex lock;
   mutex_init(&lock);
   // 获取互斥锁（阻塞等待）
   mutex_lock(&lock);
   // 尝试获取互斥锁（非阻塞，失败返回非 0）
   mutex_trylock(&lock);
   // 释放互斥锁
   mutex_unlock(&lock);
   ```
3. **典型场景**：
   - 驱动中进程上下文的设备访问控制（如文件读写）。
   - 需要长时间持有锁的业务逻辑（如数据拷贝、硬件初始化）。

#### 核心差异深度解析
##### 1. 等待机制
- **自旋锁**：
  - 等待时执行 `while (锁被占用)` 循环，CPU 100% 占用。
  - 适合临界区极短的场景（自旋耗时 < 上下文切换耗时）。
- **互斥锁**：
  - 等待时调用 `schedule()` 让出 CPU，进程进入 `TASK_INTERRUPTIBLE` 状态。
  - 适合临界区较长的场景（睡眠耗时 < 自旋耗时）。

##### 2. 上下文兼容性
| 上下文类型   | 自旋锁 | 互斥锁 |
| ------------ | ------ | ------ |
| 中断上下文   | ✅ 允许 | ❌ 禁止 |
| 进程上下文   | ✅ 允许 | ✅ 允许 |
| 持有锁时调度 | ❌ 禁止 | ✅ 允许 |

##### 3. 性能对比
- **短临界区（< 100 指令）**：自旋锁更快（无上下文切换开销）。
- **长临界区（> 100 指令）**：互斥锁更优（避免 CPU 空转）。
- **单 CPU 场景**：自旋锁几乎无意义（自旋时无法释放 CPU，必然等待到锁释放）。

#### 复试/面试高频考点
- **Q**：为什么中断上下文不能使用互斥锁？
  - A：互斥锁获取失败时会调用 `schedule()` 让进程睡眠，但中断上下文没有进程上下文，无法被调度，会导致系统死锁。
- **Q**：持有自旋锁时为什么不能执行阻塞操作？
  - A：自旋锁持有期间会屏蔽本地中断，若执行阻塞操作（如睡眠），CPU 无法响应中断，且自旋锁不会释放，其他进程/中断无法获取锁，最终导致系统卡死。
- **Q**：RTC 中断处理函数中为什么用自旋锁而不是互斥锁？
  - A：RTC 中断处理函数运行在**中断上下文**，无法使用会导致睡眠的互斥锁；且临界区仅为变量读写（极短），自旋锁的低开销更适合。
- **Q**：如何选择自旋锁和互斥锁？
  - A：核心看两个维度：
    1. 上下文：中断上下文只能用自旋锁；进程上下文按需选择。
    2. 临界区长度：短临界区用自旋锁，长临界区用互斥锁。

### 总结
1. 自旋锁适用于**中断上下文+短临界区**，通过 CPU 自旋等待实现，无上下文切换开销但会占用 CPU；互斥锁适用于**进程上下文+长临界区**，通过睡眠等待实现，有上下文切换开销但不浪费 CPU。
2. 中断上下文绝对禁止使用互斥锁，持有自旋锁时禁止执行任何阻塞操作，这是内核编程的核心规则。
3. 选择锁的核心原则：优先看上下文（中断/进程），再看临界区长度，避免“长临界区用自旋锁导致 CPU 空转”或“中断上下文用互斥锁导致死锁”。

# 7.6 中断上下文
### 中断上下文的时间限制与设计原则
#### 核心特性与时间限制
- 中断上下文会**打断其他正在执行的代码**（甚至可能打断其他中断线的处理程序），因此具有严格的时间约束。
- 中断处理代码必须**迅速、简洁**，避免使用循环处理繁重任务，防止长时间占用 CPU 导致系统响应延迟。

#### 异步执行的影响
- 中断是**异步执行**的，会随机插入到正常代码流中，若处理耗时过长，会严重影响系统实时性和其他任务的执行。
- 长时间的中断处理会导致：
  - 被打断的进程/中断响应延迟
  - 其他硬件中断无法及时处理，可能引发数据丢失或系统异常
  - 内核调度器无法正常工作，导致系统卡顿

#### 工作分离原则：下半部机制
- 核心思想：将**必须立即处理的紧急操作**（如硬件寄存器读写、清中断标志）放在中断处理程序（上半部）执行，将**耗时、非紧急的工作**（如数据拷贝、算法处理）分离到**下半部（bottom half）**中延迟执行。
- 下半部可以在更合适的时机运行（如内核空闲时、进程上下文），既保证了中断响应速度，又能完成复杂的后续处理。
- 常见的下半部实现机制：`tasklet`、`workqueue`、`softirq`。

#### 复试/面试考点提示
- **Q**：为什么中断处理程序必须尽可能简短？
  - A：因为中断上下文会打断其他代码，若处理耗时过长，会导致系统响应延迟、其他中断无法及时处理，甚至引发系统死锁或数据丢失，破坏系统实时性。
- **Q**：什么是下半部机制？为什么要引入下半部？
  - A：下半部是内核中用于延迟处理中断后续工作的机制。引入它的目的是将中断处理程序中的耗时操作分离出去，让中断处理程序尽可能快速完成，保证系统对硬件中断的实时响应。
- **Q**：中断上下文和进程上下文的核心区别是什么？
  - A：中断上下文是异步执行的，没有进程上下文，不能执行阻塞操作；进程上下文是同步执行的，属于某个进程，可以执行阻塞操作（如睡眠、I/O）。

#### 扩展关联
- 与自旋锁的关系：中断上下文只能使用自旋锁，不能使用互斥锁（互斥锁会导致睡眠，中断上下文无法调度）。
- 与 `wake_up_interruptible()`/`kill_fasync()` 的关系：这些函数是将工作延后到进程上下文的典型手段，避免在中断处理程序中执行耗时操作。

# 7.8 /proc/interrupts
### procfs 虚拟文件系统
#### 核心定义与特性
- **procfs** 是一个**虚拟文件系统**，仅存在于内核内存中，通常挂载在 `/proc` 目录。
- 读写 `/proc` 下的文件时，实际会调用内核函数，模拟对真实文件的读写操作，本质是**内核向用户态导出信息的接口**。

#### 典型应用：/proc/interrupts
- `/proc/interrupts` 是 procfs 的典型代表，用于存放**系统中断相关的统计信息**。
- 单处理器 PC 上的输出示例，会展示各中断线的触发次数、所属中断控制器及注册设备名称等，方便调试和性能分析。

#### 核心作用与设计思想
- **内核态与用户态的桥梁**：无需修改内核代码，用户态即可通过文件读写方式获取内核运行时数据（如中断计数、进程信息、内存状态）。
- **无磁盘存储**：所有数据在内存中动态生成，读取时实时计算，不占用磁盘空间，重启后数据重置。
- **调试与监控**：是系统调试、性能分析、故障排查的重要工具，例如通过 `/proc/interrupts` 观察中断分发是否均衡、是否存在异常中断风暴。

#### 复试/面试考点提示
- **Q**：为什么 procfs 被称为“虚拟文件系统”？
  - A：因为它不对应实际磁盘文件，所有内容由内核在内存中动态生成，读写操作本质是调用内核函数获取/设置内核数据，而非访问磁盘。
- **Q**：/proc/interrupts 的作用是什么？
  - A：用于查看系统中各中断线的触发次数、所属设备等统计信息，可用于分析中断负载、排查中断丢失或异常触发的问题。
- **Q**：procfs 和普通文件系统的区别？
  - A：普通文件系统存储持久化数据到磁盘；procfs 是内存态虚拟文件，数据由内核动态生成，主要用于内核与用户态的信息交互，不提供持久化存储。

#### 扩展关联
- 与中断子系统的关系：`/proc/interrupts` 由内核中断子系统维护，每次中断处理时更新计数，是 `request_irq()`/`free_irq()` 管理的中断线状态的直观展示。
- 其他常见 `/proc` 文件：`/proc/cpuinfo`（CPU 信息）、`/proc/meminfo`（内存信息）、`/proc/pid/`（进程相关信息）。

# 7.9 中断控制
### 内核中断控制接口
#### 核心接口与位置
- Linux 内核提供了一组**体系结构相关**的接口，用于操作机器的中断状态：
  - 功能：禁止当前处理器的中断系统，或屏蔽整条中断线。
  - 头文件位置：`<asm/system.h>`、`<asm/irq.h>`。
  - 完整列表：后续章节表 7-2。

#### 控制中断的核心目的：同步
- 控制中断的本质原因是**提供同步保护**：
  1.  禁止中断 → 确保当前代码不会被中断处理程序抢占。
  2.  禁止中断 → 同时会禁止内核抢占（防止当前进程被调度）。
- **关键局限**：
  - 禁止中断 / 禁止内核抢占，**无法防止来自其他处理器（CPU）的并发访问**。
  - 在 SMP（多处理器）架构下，仅靠禁止中断不足以保护共享数据。

#### 锁 + 禁止中断：完整同步方案
- 内核代码通常需要**锁 + 禁止本地中断**的组合来实现完整同步：
  - **锁（如自旋锁）**：防止来自**其他处理器**的并发访问。
  - **禁止本地中断**：防止来自**本地其他中断处理程序**的并发访问。
- 分工明确：
  - 锁：保护多 CPU 之间的共享资源竞争。
  - 禁止中断：保护中断上下文与当前代码之间的竞争。

#### 复试/面试考点提示
- **Q**：为什么仅禁止中断不能实现多处理器下的同步？
  - A：禁止中断只作用于**当前处理器**，无法阻止其他 CPU 同时访问共享数据，因此必须配合锁机制（如自旋锁）来防止跨 CPU 的并发竞争。
- **Q**：锁和禁止中断的分工是什么？
  - A：锁用于防止**其他处理器**的并发访问；禁止中断用于防止**本地其他中断处理程序**的并发访问，两者结合才能在 SMP 环境下实现完整的临界区保护。
- **Q**：为什么中断控制接口与体系结构相关？
  - A：中断控制器（如 PIC/APIC）、中断屏蔽寄存器的实现是硬件相关的，不同架构（x86/ARM/MIPS）的中断控制逻辑不同，因此接口需要与体系结构绑定。

#### 扩展关联
- 与自旋锁的关系：`spin_lock_irq()` 内部会自动调用禁止本地中断的接口，是“锁 + 禁止中断”方案的典型实现。
- 与内核抢占的关系：禁止中断会隐式禁止内核抢占，因为抢占发生在时钟中断处理中。

---
### 为什么禁止中断可以禁止内核抢占？
要理解这个问题，我们需要从**内核抢占的触发时机**和**中断的作用**两个角度来分析：

---

#### 1. 内核抢占的本质
内核抢占（Kernel Preemption）是指：**在内核态执行的代码，可以被更高优先级的进程或中断打断并调度出去**。
它的核心目的是提升系统实时性，但也带来了并发竞争的风险。

#### 2. 内核抢占的触发条件
内核抢占的发生，**必须依赖于时钟中断（Timer Interrupt）**：
- 系统时钟中断会周期性触发（比如每 1ms 或 10ms）。
- 在时钟中断处理函数中，内核会检查当前进程的时间片是否耗尽，或者是否有更高优先级的进程就绪。
- 如果满足条件，就会触发调度，抢占当前正在执行的内核态代码。

#### 3. 禁止中断如何阻断抢占
当我们调用接口（如 `local_irq_disable()`）**禁止当前处理器的本地中断**时：
1.  **时钟中断被屏蔽**：所有硬件中断（包括时钟中断）都无法传递到当前 CPU。
2.  **调度检查无法执行**：没有时钟中断，内核就没有机会执行“时间片耗尽/优先级检查”的逻辑。
3.  **调度器无法触发**：调度器的核心逻辑依赖于中断上下文的触发，没有中断就无法发起抢占操作。

因此，**禁止本地中断 = 屏蔽时钟中断 = 阻断内核抢占的触发源**，从而实现了“禁止内核抢占”的效果。

---

#### 4. 关键补充说明
- **范围限制**：禁止中断仅对**当前处理器**有效，无法阻止其他 CPU 的抢占或并发访问。
- **隐式关系**：禁止中断是“因”，禁止内核抢占是“果”——内核抢占本身没有独立的开关，它是依赖于中断机制的副作用。
- **例外情况**：在明确调用 `schedule()` 主动放弃 CPU 时，即使禁止了中断，也会发生调度（但这是主动调度，不是抢占）。

---

#### 5. 复试/面试考点总结
- **Q**：禁止中断为什么能禁止内核抢占？
  - A：因为内核抢占**必须由时钟中断触发**，而禁止中断会屏蔽包括时钟中断在内的所有本地中断，导致调度器无法执行抢占检查，从而间接实现了禁止内核抢占的效果。
- **Q**：禁止中断和禁止内核抢占是一回事吗？
  - A：不是。禁止中断是直接屏蔽硬件中断，而禁止内核抢占是禁止中断带来的**间接结果**；内核抢占还有其他触发方式（如主动调度），但在中断被屏蔽时，被动抢占无法发生。

---

## 7.9.3 中断系统的状态
### 中断上下文检查宏（`in_interrupt()` / `in_irq()`）
#### 核心宏定义与头文件
- 头文件位置：`<linux/hardirq.h>`
- 提供两个用于检查内核当前执行上下文的宏：
  - `in_interrupt()`
  - `in_irq()`

#### 宏功能与区别
| 宏 | 返回非 0 的条件 | 含义说明 |
|----|----------------|----------|
| `in_interrupt()` | 内核处于**任何类型的中断处理中** | 包括：<br>• 正在执行**中断处理程序（上半部）**<br>• 正在执行**下半部处理程序（tasklet/softirq 等）** |
| `in_irq()` | 内核**确实正在执行中断处理程序** | 仅指**硬件中断处理程序（上半部）**，不包含下半部 |

#### 典型使用场景
- 检查是否处于**进程上下文**：
  - 若 `in_interrupt() == 0` → 内核当前在**进程上下文**，可以执行睡眠、阻塞操作（如 `msleep()`、`mutex_lock()`）。
  - 若 `in_interrupt() != 0` → 内核当前在**中断/下半部上下文**，禁止执行任何阻塞操作。
- 区分硬件中断和下半部：
  - 若 `in_irq() != 0` → 明确处于硬件中断上下文。
  - 若 `in_interrupt() != 0` 但 `in_irq() == 0` → 处于下半部（softirq/tasklet）上下文。

#### 复试/面试考点提示
- **Q**：`in_interrupt()` 和 `in_irq()` 的区别是什么？
  - A：`in_interrupt()` 覆盖范围更广，包含**硬件中断 + 下半部**；`in_irq()` 仅检测**硬件中断处理程序**。
- **Q**：如何判断当前是否可以执行睡眠操作？
  - A：通过 `in_interrupt() == 0` 确认处于进程上下文，此时才允许调用 `msleep()`、`mutex_lock()` 等阻塞函数。
- **Q**：为什么需要区分这些上下文？
  - A：不同上下文有严格限制：中断上下文不能阻塞、不能调度；进程上下文则可以执行更丰富的操作，区分后能避免代码在错误上下文执行导致系统崩溃。

#### 扩展关联
- 与中断上下文限制的关系：这两个宏是内核代码安全执行的“哨兵”，避免在中断上下文执行非法操作。
- 与下半部机制的关系：`in_interrupt()` 能识别下半部，说明下半部仍属于“中断类上下文”，同样不能执行阻塞操作。
