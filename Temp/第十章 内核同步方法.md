# 10.1 原子操作
### ⚛️ 原子操作：同步机制的基石
#### 1. 核心定义
原子操作是**不可被打断的指令序列**，执行过程要么完全完成，要么完全不执行，不会出现中间状态，保证了操作的原子性。
- 类比“原子”：原子是不可分割的微粒，原子操作也因此得名，代表**不可分割的指令**。

#### 2. 核心作用
- 避免并发竞争：将原本多步的操作（如“读取变量 → 增加变量 → 写回变量”）封装为**单步原子执行**，防止多线程/多 CPU 并发访问时出现数据不一致。
- 示例：原子加操作
  - 普通加操作：`val = val + 1` 分为读、加、写三步，可能被打断导致竞争；
  - 原子加操作：三步合并为一个不可分割的指令，保证结果始终一致。

#### 3. 地位
原子操作是**其他同步方法（锁、信号量等）的底层基石**，所有高级同步机制最终都依赖硬件提供的原子指令来实现。

---

### ✅ 复试/面试速记
1.  **原子操作本质**：不可被打断的指令，执行过程无中间状态。
2.  **核心价值**：避免并发竞争，保证多线程/多 CPU 下数据操作的一致性。
3.  **地位**：是锁、信号量等高级同步机制的底层基础。

---
## 10.1.1 原子整数操作
### ⚛️ `atomic_t` 类型：原子整数操作的专用类型
#### 1. 定义与来源
`atomic_t` 是 Linux 内核中用于原子整数操作的专用类型，定义在 `<linux/types.h>` 中：
```c
typedef struct {
    volatile int counter;
} atomic_t;
```
- 本质是封装了 `volatile int` 的结构体，确保编译器不会优化内存访问。

---

#### 2. 不直接使用 `int` 的三个核心原因
1.  **类型安全约束**
    - 强制原子函数只接收 `atomic_t` 类型，避免原子操作与普通操作混用（比如对同一个变量时而用原子操作、时而用普通操作），保证操作一致性。
    - 防止 `atomic_t` 数据被传递给非原子函数，避免意外的并发竞争。

2.  **避免编译器优化干扰**
    - `volatile` 修饰 + 结构体封装，确保编译器不会对 `counter` 做别名优化或寄存器优化，保证原子操作始终访问**真实内存地址**，而非别名或缓存值。

3.  **跨体系结构兼容性**
    - 不同硬件架构（如 x86、ARM、SPARC）的原子操作实现差异很大，`atomic_t` 作为抽象类型可以**屏蔽底层差异**，让内核代码在不同平台上保持一致。

---

#### 3. 特殊限制：24 位有效位
- 尽管 Linux 支持的机器整型是 32 位，但 `atomic_t` 代码只能将其当作 **24 位** 使用。
- 原因：**SPARC 体系结构** 的原子操作实现特殊，需要额外 8 位用于锁计数等底层逻辑，因此内核统一限制为 24 位有效位。

---

### ✅ 复试/面试速记
1.  **`atomic_t` 作用**：专门用于原子整数操作，保证类型安全、避免编译器优化、跨平台兼容。
2.  **不直接用 `int` 的原因**：类型约束、防编译器优化、屏蔽架构差异。
3.  **24 位限制**：因 SPARC 架构实现特殊，统一限制有效位为 24 位。

---
### ⚛️ `atomic_t` 定义与基础操作
#### 1. 定义与初始化
```c
atomic_t v;          // 定义原子变量 v
atomic_t u = ATOMIC_INIT(0);  // 定义并初始化为 0（宏初始化）
```
- `ATOMIC_INIT(n)`：编译期初始化宏，用于给 `atomic_t` 赋初值。

---

#### 2. 核心原子操作示例
```c
atomic_set(&v, 4);    // 原子地设置 v = 4
atomic_add(2, &v);    // 原子地 v += 2 → v = 6
atomic_inc(&v);       // 原子地 v += 1 → v = 7
```
- 所有操作均为**不可打断的原子执行**，保证并发下数据一致。

#### 3. 读取与类型转换
```c
int val = atomic_read(&v);  // 原子地读取 v 的值，转换为 int 类型
printk("%d\n", val);        // 输出 7
```
- `atomic_read()` 实现（典型）：
  ```c
  static inline int atomic_read(const atomic_t *v)
  {
      return v->counter;  // 直接访问封装的 volatile int
  }
  ```
- 原理：在多数体系结构上，**字的读取本身就是原子操作**（写入期间无法并发读取），因此 `atomic_read()` 可直接返回 `counter` 成员，无需额外同步。

---

#### 4. 实现特性
- **实现方式**：原子操作通常是**内联函数**，底层依赖**内嵌汇编指令**（如 `lock` 前缀指令）实现不可打断性；本身天然原子的操作（如读取）常定义为**宏**，进一步提升效率。
- **类型安全**：所有操作仅接收 `atomic_t*` 类型，避免与普通 `int` 混用，保证操作一致性。

---

### ✅ 复试/面试速记
1.  **初始化**：`ATOMIC_INIT(n)` 用于编译期初始化 `atomic_t`。
2.  **核心操作**：`atomic_set`/`atomic_add`/`atomic_inc` 等均为原子执行。
3.  **读取**：`atomic_read()` 依赖硬件字读取原子性，直接返回 `counter` 成员。
4.  **实现**：内联函数+内嵌汇编，天然原子操作常实现为宏。

---
## 10.1.3 原子位操作
### 🧩 原子位操作核心概念
#### 1. 基本定位
- 原子位操作是内核提供的**位级别原子操作**，与体系结构相关，定义在 `<asm/bitops.h>` 中。
- 与原子整数操作不同：**没有特殊数据类型**，直接对普通内存地址操作。

---

#### 2. 操作参数与位号规则
- **参数**：`(指针, 位号 nr)`
  - 指针：指向要操作的内存（任意数据类型均可）
  - 位号：从 **0 开始计数**，0 是给定地址的最低有效位（LSB）
- **位号范围**：
  - 32 位机器：0 ~ 31 为当前字，32 为下一个字的最低位
  - 64 位机器：0 ~ 63 为当前字，64 为下一个字的最低位
  - 内核**不限制位号范围**，可跨字操作

---

#### 3. 关键特性
- **无特殊类型**：不像 `atomic_t` 封装，直接对任意内存地址的位进行原子修改。
- **原子性保证**：位的修改（置位/清位/翻转）是不可打断的，避免并发竞争。
- **跨平台兼容**：底层由体系结构相关的汇编指令实现（如 `lock bts`），内核接口统一。

---

### ✅ 复试/面试速记
1.  **定义位置**：`<asm/bitops.h>`，与体系结构强相关。
2.  **操作对象**：普通内存地址，无特殊数据类型。
3.  **位号规则**：0 为最低位，可跨字操作，内核不限制范围。
4.  **核心差异**：与 `atomic_t` 相比，位操作更灵活，可作用于任意内存位。

---

# 10.2 自旋锁
### 🔒 自旋锁（Spin Lock）核心概念
#### 1. 基本特性
- **Linux 内核最常见的锁类型**，属于**独占锁**：**最多只能被一个执行线程持有**。
- **互斥保障**：任意时刻，自旋锁能防止多于一个执行线程同时进入临界区。
- **适用场景**：保护共享数据的所有并发访问，实现同步。

---

#### 2. 争用与等待行为
- **锁争用（Contention）**：当线程尝试获取**已被持有**的自旋锁时，不会进入睡眠/调度，而是**一直忙循环（自旋/旋转）**，直到锁被释放、重新可用。
- **无争用场景**：若锁未被占用，请求线程会**立刻获取锁**，继续执行，无额外开销。

---

#### 3. 关键特点总结
| 特性 | 说明 |
|------|------|
| **持有者数量** | 同一时间仅 1 个线程可持有 |
| **等待方式** | 忙循环（自旋），不释放 CPU |
| **上下文限制** | 适合**中断上下文/短临界区**（避免长时间自旋占用 CPU） |
| **核心价值** | 避免进程切换开销，**短时间等待**时效率高于睡眠锁 |
| **保护范围** | 可在多个位置保护同一份共享数据，保证所有访问同步 |

---

### ✅ 复试/面试速记
1.  **定义**：Linux 内核最常见的独占锁，同一时间仅一个线程持有。
2.  **等待逻辑**：争用时忙循环自旋等待，无争用时立刻获取锁。
3.  **优势**：避免进程切换开销，适合**短临界区、中断上下文**；劣势是长时间自旋会浪费 CPU。
4.  **作用**：防止多个线程同时进入临界区，保护共享数据并发安全。

---
### 🔒 自旋锁在中断上下文的使用规则
#### 1. 适用场景
自旋锁**可以在中断处理程序中使用**（信号量等会导致睡眠的锁不能用，因为中断上下文不允许调度/睡眠）。

---

#### 2. 关键安全要求：获取锁前必须禁止本地中断
- **原因**：如果不先禁止当前处理器的中断，中断处理程序可能会打断**正持有锁的内核代码**，并尝试争用同一个已被持有的自旋锁。
- **死锁风险**：
  1.  中断处理程序开始自旋，等待锁释放；
  2.  锁的持有者被中断打断，必须等中断处理程序执行完才能继续运行、释放锁；
  3.  两者互相等待，形成**双重请求死锁**。

---

#### 3. 范围限制：只需要禁止当前处理器的中断
- 只需要关闭**当前 CPU** 的中断：
  - 若中断发生在**其他处理器**上，即使中断处理程序在同一锁上自旋，也不会阻塞锁的持有者（在不同 CPU 上）最终释放锁。
- 多处理器环境下，跨 CPU 的自旋不会导致死锁，只有**同一 CPU 上的中断抢占**才会引发死锁。

---

### ✅ 复试/面试速记
1.  **中断上下文可用自旋锁**，但不能用会睡眠的锁（如信号量）。
2.  **获取自旋锁前必须先禁止当前处理器的本地中断**，防止双重请求死锁。
3.  只需禁止当前 CPU 的中断，其他 CPU 的中断不影响锁的释放。

---

## 10.2.2 其他针对自旋锁的操作
### 🔒 自旋锁核心 API 速查表
| 方法 | 描述 | 适用场景 |
|------|------|----------|
| `spin_lock()` | 获取指定自旋锁（不禁止中断） | **进程上下文**，无中断嵌套风险 |
| `spin_lock_irq()` | 禁止本地中断 + 获取锁 | **中断上下文/进程+中断共享数据**，已知之前中断是开启状态 |
| `spin_lock_irqsave()` | 保存当前中断状态 → 禁止本地中断 → 获取锁 | **中断上下文/进程+中断共享数据**，**不知道之前中断状态**（最安全） |
| `spin_unlock()` | 释放指定自旋锁 | 对应 `spin_lock()` |
| `spin_unlock_irq()` | 释放锁 + 激活本地中断 | 对应 `spin_lock_irq()` |
| `spin_unlock_irqrestore()` | 释放锁 + 恢复之前保存的中断状态 | 对应 `spin_lock_irqsave()`（最安全，恢复原状态） |
| `spin_lock_init()` | 动态初始化 `spinlock_t` | 运行期创建自旋锁 |
| `spin_trylock()` | 尝试获取锁，未获取则返回非 0 | **非阻塞获取锁**，避免长时间自旋 |
| `spin_is_locked()` | 检查锁是否被持有（被持有返回非 0） | 状态查询 |

---

### ✅ 关键配对规则
- `spin_lock()` ↔ `spin_unlock()`
- `spin_lock_irq()` ↔ `spin_unlock_irq()`
- `spin_lock_irqsave(flags)` ↔ `spin_unlock_irqrestore(flags)`

### 📌 复试/面试重点
1.  **中断上下文必须用 `spin_lock_irq()`/`spin_lock_irqsave()`**，防止死锁。
2.  **`spin_lock_irqsave()` + `spin_unlock_irqrestore()` 是最通用、最安全的组合**，不依赖之前中断状态。
3.  `spin_trylock()` 用于避免长时间自旋，适合需要快速判断的场景。

## 10.2.3 自旋锁和下半部
### 🧩 不同上下文共享数据的同步保护规则
#### 一、跨上下文共享数据
1.  **进程上下文 ↔ 下半部**
    - 下半部可抢占进程上下文，因此必须：
      - 对共享数据**加锁**（如自旋锁）
      - 同时**禁止下半部执行**，防止下半部抢占导致数据竞争

2.  **中断处理程序 ↔ 下半部**
    - 中断处理程序可抢占下半部，因此必须：
      - 对共享数据**加锁**
      - 同时**禁止中断**，防止中断抢占引发死锁或数据混乱

---

#### 二、tasklet 内部同步规则
- **同类 tasklet**：内核保证同类 tasklet 不会同时运行（即使在多 CPU 上），因此**共享数据无需额外保护**。
- **不同类 tasklet**：若共享数据，需要：
  - 获取**普通自旋锁**保护数据
  - **无需禁止下半部**：同一 CPU 上不会出现 tasklet 相互抢占的情况

---

#### 三、软中断内部同步规则
- 无论是否**同种类型**，只要软中断之间共享数据，就必须：
  - 用锁（如自旋锁）保护共享数据（因为同种软中断可在多 CPU 上并行执行）
- **无需禁止下半部**：同一 CPU 上的软中断不会抢占另一个软中断

---

### ✅ 复试/面试速记表
| 共享场景 | 保护措施 | 特殊说明 |
|----------|----------|----------|
| 进程 ↔ 下半部 | 加锁 + 禁止下半部 | 防止下半部抢占 |
| 中断 ↔ 下半部 | 加锁 + 禁止中断 | 防止中断抢占 |
| 同类 tasklet | 无需保护 | 内核保证串行执行 |
| 不同类 tasklet | 加普通自旋锁 | 无需禁止下半部 |
| 软中断（任意类型） | 加锁保护 | 无需禁止下半部 |

# 10.3 读-写自旋锁
### 📖 读写自旋锁（rwlock）核心知识点
#### 1. 基本特性
- 也叫**共享/排他锁**、**并发/排斥锁**：
  - **读锁（共享）**：多个读任务可**并发持有**，读与读之间不互斥
  - **写锁（排他）**：最多只能被**一个写任务持有**，且写时不允许并发读操作
- 适用场景：**读多写少**的数据结构（如读/写、生产者/消费者模型）

---

#### 2. 基本使用示例
```c
// 1. 定义并初始化读写锁
DEFINE_RWLOCK(mr_rwlock);

// 2. 读者分支（只读）
read_lock(&mr_rwlock);
/* 临界区（只读操作） */
read_unlock(&mr_rwlock);

// 3. 写者分支（读写）
write_lock(&mr_rwlock);
/* 临界区（读写操作） */
write_unlock(&mr_rwlock);
```

---

#### 3. 重要禁忌：不能“升级”读锁为写锁
- 错误示例：
  ```c
  read_lock(&mr_rwlock);
  write_lock(&mr_rwlock);  // ❌ 死锁！
  ```
- 死锁原因：写锁会自旋等待**所有读者释放锁**，但当前线程本身就是读者，永远无法释放读锁，导致自己死等。
- 正确做法：需要写操作时，**一开始就直接请求写锁**；若读写无法清晰分离，应改用普通自旋锁。

---

#### 4. 额外特性与中断场景
- **读锁可递归**：同一个线程可多次获取同一读锁，不会死锁。
- **中断上下文使用**：
  - 若中断处理程序只有读操作：可用 `read_lock()`（无需保存中断状态）
  - 若有写操作：必须用 `write_lock_irqsave()` 禁止中断，否则中断里的读操作可能锁死在写锁上。

---

### 🔒 自旋锁 vs 信号量 选型指南
| 锁类型 | 适用场景 | 核心特点 |
|--------|----------|----------|
| **自旋锁** | 加锁时间**短**、代码**不会睡眠**（如中断处理程序） | 忙循环等待，无上下文切换开销，延迟低 |
| **信号量** | 加锁时间**可能很长**、持有锁时代码**可能睡眠** | 会阻塞并调度让出 CPU，适合长临界区 |

---

### ✅ 复试/面试速记
1.  **读写锁**：读共享、写排他，适合读多写少场景；**严禁读锁升级为写锁**。
2.  **自旋锁**：短临界区、不可睡眠场景首选；中断上下文需配合 `irqsave/irqrestore` 使用。
3.  **信号量**：长临界区、允许睡眠时使用，会主动调度让出 CPU。

---

# 10.4 信号量
### 🛑 信号量（Semaphore）核心知识点
#### 1. 基本定义：睡眠锁
信号量是一种**睡眠锁**：
- 当任务尝试获取**已被占用**的信号量时，会被加入**等待队列**并进入**睡眠状态**，让出 CPU 执行其他代码。
- 当信号量被释放后，等待队列中的任务会被唤醒，重新尝试获取信号量。

---

#### 2. 核心特性与结论
- **适用场景**：锁被**长时间持有**的场景（如芯片复位、I/O 等待、长临界区），因为等待时会睡眠，不浪费 CPU。
- **不适用场景**：锁被**短时间持有**的场景，因为睡眠/唤醒、维护等待队列的开销可能超过锁占用时间。
- **上下文限制**：**只能在进程上下文获取信号量**，中断上下文无法调度/睡眠，因此不能使用信号量。
- **持有期间可睡眠**：持有信号量时可以睡眠，不会导致死锁（其他等待任务只会继续睡眠）。
- **锁嵌套禁忌**：**不能同时持有自旋锁和信号量**，因为等待信号量时可能睡眠，而持有自旋锁时禁止睡眠，会引发死锁。

---

#### 3. 信号量 vs 自旋锁 关键差异
| 特性 | 信号量 | 自旋锁 |
|------|--------|--------|
| 等待方式 | 睡眠，让出 CPU | 忙循环（自旋），占用 CPU |
| 适用场景 | 长临界区、可睡眠 | 短临界区、不可睡眠（如中断上下文） |
| 上下文限制 | 仅进程上下文 | 可用于中断/进程上下文 |
| 持有期间 | 允许睡眠 | **禁止睡眠/调度** |
| 内核抢占 | 不禁止抢占，代码可被调度 | 禁止抢占，持有期间不会被调度 |

---

#### 4. 选型建议
- 若代码需要**睡眠**（如和用户空间同步、硬件等待），**必须用信号量**。
- 若锁持有时间**短**且代码**不会睡眠**（如中断处理），用**自旋锁**更高效。
- 信号量对调度延迟影响更小，因为不会禁止内核抢占。

---

### ✅ 复试/面试速记
1.  **信号量是睡眠锁**：争用时睡眠，释放后唤醒，适合长临界区。
2.  **只能在进程上下文使用**，中断上下文不能用。
3.  **持有信号量可睡眠**，但不能同时持有自旋锁。
4.  选型依据：**锁持有时间长短 + 是否允许睡眠**。

---
## 10.4.1 计数信号量和二值信号量
### 🧩 信号量的计数特性：二值信号量 vs 计数信号量
#### 1. 核心概念：使用者数量（count）
信号量允许同时持有的任务数由初始化时的 **count 值** 决定，这是它与自旋锁的核心区别：
- 自旋锁：同一时刻最多 **1 个** 持有者
- 信号量：同一时刻最多 **count 个** 持有者

---

#### 2. 二值信号量（互斥信号量）
- **count = 1**
- 行为：同一时刻最多 1 个任务持有锁，和自旋锁一样实现**互斥访问**
- 别名：二值信号量（要么被持有，要么空闲）、互斥信号量（强制互斥）
- 内核使用：**最常用**，几乎所有信号量场景都用它来做互斥保护

#### 3. 计数信号量（Counting Semaphore）
- **count > 1**
- 行为：同一时刻最多 `count` 个任务同时进入临界区，**不提供互斥**，而是做**资源限制**
- 用途：限制同时访问某类资源的任务数量（比如限制最多 N 个并发 I/O 请求）
- 内核使用：机会很少，仅在需要资源限流时使用

---

### ✅ 复试/面试速记
1.  **信号量 count**：决定同时允许的持有者数量，初始化时指定
2.  **二值信号量（count=1）**：实现互斥，和自旋锁功能等价，是内核最常用的信号量类型
3.  **计数信号量（count>1）**：实现资源限流，不提供互斥，内核中很少用

---

## 10.4.2 创建和初始化信号量
### 🧩 信号量的定义与初始化方式
信号量的实现与体系结构相关，定义在 `<asm/semaphore.h>` 中，用 `struct semaphore` 类型表示。

---

#### 1. 静态声明与初始化
- **通用静态信号量**：
  ```c
  struct semaphore name;        // 声明信号量变量
  sema_init(&name, count);      // 初始化，count 为使用者数量
  ```
- **静态互斥信号量（快捷方式）**：
  ```c
  static DECLARE_MUTEX(name);   // 直接声明并初始化为互斥信号量（count=1）
  ```

---

#### 2. 动态创建与初始化
当信号量作为大数据结构的一部分动态创建时，使用指针初始化：
- **通用动态信号量**：
  ```c
  sema_init(sem, count);  // sem 是指向 struct semaphore 的指针，count 为使用者数量
  ```
- **动态互斥信号量**：
  ```c
  init_MUTEX(sem);  // 初始化指针 sem 指向的信号量为互斥类型（count=1）
  ```

---

### ✅ 复试/面试速记
1.  **类型**：`struct semaphore`，体系结构相关。
2.  **静态互斥**：`DECLARE_MUTEX(name)` 最常用，直接生成二值信号量。
3.  **动态互斥**：`init_MUTEX(sem)` 用于指针形式的互斥信号量初始化。

---

## 10.4.3 使用信号量
### 🧩 信号量核心操作 API 速览
#### 1. 初始化相关函数
| 函数 | 功能描述 |
|------|----------|
| `sema_init(struct semaphore *, int)` | 以指定计数值初始化动态信号量 |
| `init_MUTEX(struct semaphore *)` | 初始化为互斥信号量（count=1） |
| `init_MUTEX_LOCKED(struct semaphore *)` | 初始化为加锁状态（count=0） |

---

#### 2. 获取信号量函数
| 函数 | 功能描述 |
|------|----------|
| `down(struct semaphore *)` | 不可中断获取：争用时进入**不可中断睡眠** |
| `down_interruptible(struct semaphore *)` | 可中断获取：争用时进入**可中断睡眠**，被信号唤醒时返回非0 |
| `down_trylock(struct semaphore *)` | 非阻塞获取：若信号量被占用，**立刻返回非0**；否则获取成功返回0 |

---

#### 3. 释放信号量函数
| 函数 | 功能描述 |
|------|----------|
| `up(struct semaphore *)` | 释放信号量：若等待队列非空，唤醒其中一个任务 |

---

### ✅ 代码示例
```c
// 定义互斥信号量
static DECLARE_MUTEX(mr_sem);

// 可中断方式获取信号量
if (down_interruptible(&mr_sem)) {
    // 被信号中断，未获取到信号量
    return -EINTR;
}

/* 临界区：安全访问共享资源 */

// 释放信号量
up(&mr_sem);
```

---

### 📌 关键注意点
- **`down_interruptible()` 更安全**：推荐使用，可被信号唤醒，避免进程不可中断地死等。
- **`down_trylock()` 无阻塞**：适合需要快速判断是否能获取锁的场景，不会让进程睡眠。
- **`up()` 必须成对调用**：每个成功的 `down`/`down_interruptible`/`down_trylock` 都要对应一个 `up()`，否则会导致信号量永久泄漏。

---

# 10.5 读写信号量
### 📖 读写信号量（rw_semaphore）核心知识点
#### 1. 基本特性
- 本质是**互斥信号量**（引用计数 = 1），但只对**写者互斥**，对**读者共享**：
  - 无写者时：**任意数量读者**可并发持有读锁
  - 无读者时：**唯一写者**可持有写锁
  - 读写不能同时进行
- 睡眠不可被信号打断，因此只有一个版本的 `down()` 操作（无 `interruptible` 变体）

---

#### 2. 基础 API 与使用示例
```c
// 定义并初始化读写信号量
static DECLARE_RWSEM(mr_rwsem);

// 读操作流程
down_read(&mr_rwsem);        // 获取读锁
/* 只读临界区 */
up_read(&mr_rwsem);          // 释放读锁

// 写操作流程
down_write(&mr_rwsem);       // 获取写锁
/* 读写临界区 */
up_write(&mr_rwsem);          // 释放写锁
```

---

#### 3. 非阻塞 trylock 接口
- `down_read_trylock()` / `down_write_trylock()`
  - **返回值与普通信号量相反**：
    - 成功获取锁 → 返回**非 0**
    - 锁被争用 → 返回 **0**
  - 不会阻塞，适合快速尝试获取锁的场景

---

#### 4. 特有操作：写锁降级
- `downgrade_write()`：**动态将已获取的写锁转换为读锁**
  - 适用场景：写完数据后，只需要继续读取，不需要再修改，可降级为读锁，让其他读者并发访问，提升性能
  - 比先释放写锁再获取读锁更安全（避免中间窗口被其他写者抢占）

---

### ✅ 复试/面试速记
1.  **读写互斥、读读共享**：读锁可并发，写锁独占，读写互斥
2.  **不可中断睡眠**：只有 `down_read()`/`down_write()`，无 `interruptible` 版本
3.  **trylock 返回值相反**：成功=非0，失败=0（和普通信号量相反）
4.  **特有功能**：`downgrade_write()` 可将写锁降级为读锁，优化读多写少场景

---

# 10.6 互斥体
### 🔒 Mutex（互斥体）核心知识点
#### 1. 基本特性
- 行为类似**计数为 1 的信号量**，但接口更简单、实现更高效，限制也更严格。
- 本质是**互斥锁**：任何时刻最多只有一个任务持有。

---

#### 2. 定义与初始化
- **静态定义**：
  ```c
  DEFINE_MUTEX(name);
  ```
- **动态初始化**：
  ```c
  mutex_init(&mutex);
  ```

#### 3. 核心 API
| 函数 | 描述 |
|------|------|
| `mutex_lock(&mutex)` | 上锁，不可用则睡眠 |
| `mutex_unlock(&mutex)` | 解锁 |
| `mutex_trylock(&mutex)` | 非阻塞尝试上锁：成功返回 1，失败返回 0 |
| `mutex_is_locked(&mutex)` | 检查是否被争用：是返回 1，否返回 0 |

---

#### 4. 严格使用约束（重点）
- **谁上锁谁解锁**：不能在一个上下文上锁、另一个上下文解锁，必须在同一上下文中完成。
- **禁止递归**：不能递归持有同一个 mutex，也不能重复解锁已解锁的 mutex。
- **持有期间不能退出**：持有 mutex 时进程不能退出。
- **不能在中断/下半部使用**：即使 `mutex_trylock()` 也不行。
- **只能通过官方 API 管理**：不能手动拷贝、初始化或重复初始化。

---

### 🧭 锁选型规范
#### 1. Mutex vs 信号量
- **优先使用 Mutex**：除非 Mutex 的约束限制了场景，才考虑信号量（一般是底层特殊代码）。
- Mutex 更轻量、调试更友好（打开 `CONFIG_DEBUG_MUTEXES` 可检测违规）。

#### 2. 自旋锁 vs Mutex（互斥体）选型表
| 需求 | 建议加锁方法 |
|------|--------------|
| 低开销加锁 | 优先自旋锁 |
| 短期锁定 | 优先自旋锁 |
| 长期加锁 | 优先互斥体 |
| 中断上下文加锁 | 必须用自旋锁 |
| 持有锁需要睡眠 | 必须用互斥体 |

---

### ✅ 复试/面试速记
1.  **Mutex 是简化版计数=1 的信号量**，更高效但限制更多。
2.  **核心约束**：谁上锁谁解锁、禁止递归、不能在中断/下半部使用。
3.  **选型原则**：优先 Mutex；中断上下文/短临界区用自旋锁；长临界区/可睡眠用 Mutex/信号量。

---

# 10.10 禁止抢占
### ⚙️ 内核抢占与自旋锁的关系
#### 1. 内核抢占的问题
Linux 内核是**抢占式**的：高优先级进程可以随时打断低优先级进程，这可能导致两个任务同时进入同一个临界区，引发并发数据竞争。

#### 2. 自旋锁的双重作用
- **SMP 安全**：防止多处理器（SMP）上的并发访问。
- **抢占安全**：当一个 CPU 持有自旋锁时，内核会**禁止抢占**，保证持有锁的任务不会被调度打断，从而避免抢占导致的并发问题。
- 因为内核已经是 SMP 安全的，通过自旋锁标记“非抢占区域”，内核自然也变成了**抢占安全（preempt-safe）**的。

---

#### 3. 特殊场景：Per-CPU 数据
有些数据是**每个处理器唯一（Per-CPU）**的，只会被当前 CPU 访问，理论上不需要锁保护。
但在抢占式内核中，如果没有自旋锁禁止抢占，新调度的任务可能在同一个 CPU 上访问该变量，仍然会引发并发问题。
所以：
- 即使不需要 SMP 互斥，也需要**关闭内核抢占**来保证 Per-CPU 数据的安全。

---

### ✅ 复试/面试速记
1.  **自旋锁 = SMP 互斥 + 禁止抢占**：既解决多 CPU 并发，又解决单 CPU 抢占问题。
2.  **抢占安全依赖自旋锁**：持有自旋锁时内核禁止抢占，保证临界区不被打断。
3.  **Per-CPU 数据**：无需 SMP 锁，但仍需禁止抢占，防止同一 CPU 上的任务切换导致并发访问。

---
### SMP
### 🧠 SMP 是什么？
**SMP** 是 **Symmetric Multi-Processing** 的缩写，中文叫**对称多处理**，是一种多处理器的计算机架构。

---

### ✨ 核心特点
1.  **对称**：所有 CPU（处理器）地位平等，共享同一内存、总线和 I/O 资源，没有主从之分。
2.  **多处理**：系统中存在多个物理 CPU 核心，它们可以**并行执行不同的任务/进程/线程**，提升系统吞吐和性能。
3.  **调度透明**：操作系统内核负责将任务调度到任意一个空闲 CPU 上运行，对应用程序来说，就像在一个“虚拟的单核”上运行一样。

---

### 🔒 对内核并发的影响
在 SMP 架构下，会出现新的并发问题：
- 同一时刻，**不同 CPU 上的两个进程**可能同时访问同一个共享数据（比如全局变量、硬件寄存器）。
- 这就需要内核使用**自旋锁、互斥量**等同步机制，来保护临界区，避免数据竞争。
- 你之前看到的“自旋锁让内核 SMP-safe”，就是指自旋锁能保证在多 CPU 环境下，共享数据的并发访问是安全的。

---

### 📌 简单类比
- **单核系统**：一个人（CPU）在一张桌子（内存）上干活。
- **SMP 系统**：多个人（多个 CPU）在同一张桌子（共享内存）上一起干活，需要互相配合（同步机制），避免抢同一份文件（共享数据）。

---

### 🎯 复试/面试速记
- **SMP = 对称多处理器架构**，多个 CPU 平等共享内存和资源，并行执行任务。
- 带来的核心问题：**多 CPU 并发访问共享数据**，需要自旋锁等锁机制来保证 SMP 安全。
- 和内核抢占一起，构成了 Linux 内核并发的两大来源。

---
### 🔍 为什么自旋锁能在多 CPU 下保证安全？
1.  **互斥性保证**
    自旋锁是**独占锁**：同一时刻最多只能有 **1 个 CPU 上的执行单元** 持有锁。
    - 当一个 CPU 成功获取自旋锁后，其他 CPU 上的任务尝试获取锁时，会进入**忙循环（自旋）**，直到锁被释放。
    - 这就保证了**临界区代码在任意时刻只会在一个 CPU 上执行**，完全避免了多 CPU 并行进入临界区导致的数据竞争。

2.  **禁止抢占 + 原子操作**
    - 持有自旋锁时，内核会**禁止当前 CPU 的抢占调度**，保证持有锁的任务不会被中途打断，能完整执行完临界区并释放锁。
    - 锁的获取/释放操作底层由**原子指令**（如 `test-and-set`、`compare-and-swap`）实现，保证在多 CPU 下“检查-设置”锁状态的操作不可分割，不会出现竞态。

3.  **SMP 场景的天然适配**
    - 自旋锁的“忙等待”特性在多 CPU 下是高效的：等待的 CPU 可以继续执行指令（自旋），而不是像信号量那样主动放弃 CPU 进入睡眠，避免了进程切换的开销。
    - 对于**短临界区**，忙等待的成本远低于睡眠/唤醒，非常适合内核中大量的快速同步场景。

---

### ⚠️ 注意：在单 CPU 下的特殊表现
在单 CPU、不可抢占内核中，自旋锁会被**优化为空操作**：
- 因为不存在其他 CPU 并行执行，也不会发生抢占，所以不需要忙等待，只要保证临界区不被中断打断即可。
- 但在 SMP 或可抢占内核中，自旋锁的互斥和禁止抢占逻辑才会真正生效。

---

### 📌 总结
- **多 CPU 环境下，自旋锁是保证并发安全的理想选择**：通过独占互斥 + 原子操作 + 禁止抢占，完美解决了多 CPU 并行访问共享数据的问题。
- 它的设计目标就是**高效处理 SMP 下的短临界区同步**，是 Linux 内核中最基础、最常用的同步原语之一。
