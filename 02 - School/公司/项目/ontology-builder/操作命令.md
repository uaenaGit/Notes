# 二、验证 LLM 链路代码
```powershell
@'
import asyncio

from ontology_builder_agent.config import get_settings
from mbse_harness.core.llm import LLMProvider, LLMService


async def main():
    settings = get_settings()

    service = LLMService(
        provider=LLMProvider(settings.default_llm_provider),
        model=settings.default_llm_model,
    )

    print("provider:", service.provider.value)
    print("model:", repr(service.model))
    print("base_url:", service.base_url)
    print("api_key_configured:", bool(service.api_key))

    response = await service.chat(
        messages=[
            {"role": "user", "content": "只回复 OK"}
        ],
        temperature=0.1,
        max_tokens=512,
        enable_thinking=False,
    )

    print("content:", repr(response.content))
    print("content_length:", len(response.content or ""))
    print("reasoning_length:", len(response.reasoning_content or ""))
    print("finish_reason:", response.finish_reason)
    print("error:", response.error)


asyncio.run(main())
'@ | python -
```

## 一、先看懂整条PowerShell命令
```powershell
@'
# Python代码全部写在这里
'@ | python -
```
- `@' '@`：PowerShell**多行原始字符串**，把里面所有文本当成Python源码；
- `| python -`：管道把源码传给python标准输入执行（等价于临时脚本，**不用新建test.py文件**，粘贴直接跑）。

## 二、代码功能定位：**LLM链路最小可用验证脚本**
目标：**脱离OntologyBuilderAgent本体构建整套复杂逻辑，单独抽离底层LLM模块，验证配置、连接、API调用通不通**。

### 代码执行流程拆解
```python
# 1. 加载项目配置（就是你之前一直在看的 Settings(BaseSettings)）
settings = get_settings()
```
自动读取：
- `.env.builder`环境配置文件
- 环境变量 `DEFAULT_LLM_PROVIDER / DEFAULT_LLM_MODEL`
拿到你在项目里预设的大模型厂商、模型名称。

```python
# 2. 初始化底层LLM服务类
service = LLMService(
    provider=LLMProvider(settings.default_llm_provider),
    model=settings.default_llm_model,
)
```
`LLMService` 是项目封装统一大模型接口层（兼容minimax/DeepSeek等多个厂商），**所有本体生成的LLM请求最终都是走这个类**。

```python
# 3. 打印关键配置，方便排错
print("provider:", service.provider.value)
print("model:", repr(service.model))
print("base_url:", service.base_url)
print("api_key_configured:", bool(service.api_key))
```
✅ 快速自查4个高频出错点：
1. 使用哪个模型厂商（minimax？deepseek？）
2. 模型名称是否正确
3. API接口地址有没有加载成功
4. 是否成功读到API Key（最常见问题：.env文件没加载、key为空）

```python
# 4. 发起极简对话请求
response = await service.chat(
    messages=[{"role": "user", "content": "只回复 OK"}],
    temperature=0.1,
    max_tokens=512,
    enable_thinking=False,
)
```
发送超简单prompt：**只让模型输出OK**，消除长文本、复杂推理带来的额外干扰。
`enable_thinking=False`：关闭深度思考模式，适合快速连通性测试。

```python
# 5. 打印返回结果
print("content:", repr(response.content))
print("content_length:", len(response.content or ""))
print("reasoning_length:", len(response.reasoning_content or ""))
print("finish_reason:", response.finish_reason)
print("error:", response.error)
```
重点观察：
- `error` 是否为空（不为空=API调用失败）
- `content` 是否拿到预期的`OK`
- `finish_reason`：`stop`=正常完成，`length`=被截断，`error`=异常

## 三、这个脚本解决你项目里什么痛点？
你本体构建命令（`from-text`）一旦报错，很难区分故障位置：
> 到底是【本体解析/转换代码bug】 还是 【LLM API连不通、密钥错误、模型配置错误】？

### 使用思路
1. **运行此脚本，如果失败** → 问题锁定：`.env.builder`配置、API密钥、网络、服务商接口
2. **运行此脚本，正常返回OK** → LLM底层链路没问题，问题出在：OntologyBuilderAgent、SysML提取、prompt构造、本体转换上层代码

## 四、对应你项目场景
你之前执行命令可以加`--no-llm`跳过大模型；一旦去掉`--no-llm`就依赖这套`LLMService`。
这条脚本就是**LLM模块独立冒烟测试用例**。

## 五、预期正常输出示例
```
provider: minimax
model: 'minimax-01'
base_url: https://api.minimax.chat/v1
api_key_configured: True
content: 'OK'
content_length: 2
reasoning_length: 0
finish_reason: stop
error: None
```

## 六、常见失败场景
1. `api_key_configured: False` → `.env.builder没加载成功/变量名写错
2. `error: xxx` → 网络不通、密钥无效、模型名称错误、额度耗尽
3. 无输出/卡住 → 代理/防火墙拦截API出口

如果你跑出来结果，我可以帮你直接判断LLM链路是否正常。

```powershell
Select-String -Path "D:\Work\projects\ontology-builder-work\rocket-engine-ontology\reports\faithful-build\chapter01.ttl" -Pattern "液氧|液氢|泵压式|偏二甲肼|硝酸-27S" | Measure-Object
```
注意：
改动`.java`文件后，应先`clean`，原因是 `ontology-builder` 的 Python 代码内部调 bridge 时用的是旧 jar。`ontology-builder` 的 `bridge.py` 会从 `SYSML_OWL_BRIDGE_DIR` 指向的目录找 bridge jar，那个目录里的 jar 是 `mvn install` 之前的旧版本。
**正确的验证流程：**
1. 先在 bridge 目录 `mvn clean install`（已完成）
2. 直接在 bridge 目录运行 `mvn exec:java` 转 TTL

这样用的是刚编译的最新 jar。Python 端如果要也生效，需要确认 `SYSML_OWL_BRIDGE_DIR` 环境变量指向 `D:\Work\projects\sysml-owl-bridge`，ontology-builder 运行时会自动找最新的 `target/` 下的 jar。
